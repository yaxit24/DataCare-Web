# Prospective trusted session adapter seam — Round12

This is a read-only implementation-preparation note. The pure Round12 mode resolver is not installed in authentication, session persistence, HTTP, or the ledger reader. It validates consistency of supplied facts; it does not establish their authority. No registration identifiers, decoding logic or default business mode are introduced here.

## Current seam and constraints

`web/packages/db/prisma/schema.prisma:3791–3809` defines `AuthSession` under the tenant/session composite identity. It stores login company separately from selected company/location/year, refresh-token hash, expiry and revocation. It has no selected-context epoch, mode generation, trusted bootstrap/command edition observation, exception classification or semantic-mode history. Its year storage is nullable `VARCHAR(9)`; the pure helper's broader identifier transport bound does not change this schema.

`web/apps/api/src/modules/auth/session.ts:124–140` retrieves the live session and checks subject, tenant, revocation and expiry. `web/apps/api/src/app.ts:278–318` then compares access-token scope to that stored scope and loads fresh principal rights. Those existing checks remain required. Matching scope strings do not themselves prove a unique company-opening generation: a later return to the same company/location/year must not recreate the earlier mode observation.

`session.ts:208–226` changes the selected scope without an expected generation and without mode state. `/context/select`, at `app.ts:707–751`, currently resolves permitted scope, applies the source last-day lock, updates the session scope, then issues an access token. These are separate steps. Attaching mode bootstrap after these steps would permit a partially established context; attaching it only to the token would omit authoritative persistence and command concurrency. The future adapter must deliberately reconcile this transaction boundary rather than add an independent side-effect call.

`web/apps/api/src/modules/auth/jwt.ts:8–30` has selected scope and session identity but no context/mode generation. Refresh logic in `session.ts:142–205` and password/revocation paths must retain or invalidate the corresponding authoritative state deliberately. Refresh must not re-run company-open bootstrap simply because a token rotates. A later command edition may differ from bootstrap edition without reopening the company (frozen primary `MDI_FORM.cs:11155–11247`); these observations cannot be collapsed into one edition field.

## Bounded implementation sequence

1. Establish an approved server authority for successfully completed company opening, bootstrap edition and qualified exception classification, and a separate authority for the later command edition. Preserve unknown status when any required authority is absent. Neither login rights, selected book `DATA_TYPE`, request-provided mode nor a hardcoded `A`/`C` supplies this authority.
2. Add a tenant/session-owned context epoch and independent mode generation, or a child record with equivalent transactionally enforced ownership. The record must bind selected scope, completed-open evidence revisions, bootstrap result, current result and accepted semantic history. Define expiry/revocation/backup behavior explicitly. Context identity must change on a genuine reopen, including A→B→A; whether a same-scope selection is a genuine reopen is an explicit command contract to settle before implementation.
3. Resolve scope eligibility and trusted bootstrap observations, then atomically commit selected scope, new epoch and corresponding mode state under an expected session/context generation. Reconcile the existing last-day-lock transaction before claiming complete company-open success. Rollback must leave the previous session context usable when the operation fails. Only issue the new access token after authoritative commit; a failed response after commit needs an explicit recovery observation.
4. Expose a read-only current-mode observation with context identity, mode generation, status/reason and bounded public provenance revisions. Expose semantic command submission only after a source-backed command authorization policy is agreed. The request names the expected epoch/generation and canonical semantic command; it does not carry trusted edition, complete catalog rows, previous mode or bootstrap evidence.
5. In one locked transaction, recheck session liveness and expected context/mode generation, resolve fresh command edition, observe the complete literal-company `01` catalog with physical revisions, run the pure resolver, and persist accepted history/generation. Relevant duplicates, noncanonical aliases, unavailable catalog and unsupported modes must preserve prior state. Do not map raw Windows keys in this API.
6. The downstream balance observation must consume authoritative mode and its generation together with the ledger snapshot. Scope, master/configuration versions and mode generation belong in any replay version that depends on the balance. Reading mode outside the balance transaction would not establish a coherent observation. An unresolved mode must remain an explicit unavailable closing capability.

## Required verification before integration credit

- Login/bootstrap, refresh, same-scope reopen, company/location/year changes and A→B→A each follow their declared epoch semantics; current edition changes never silently rebootstrap mode.
- Two concurrent semantic commands with the same expected generation allow one accepted transition; stale submissions preserve the current authoritative state. A failed/denied command does not erase prior history or publish a replacement token.
- Scope change, revocation, expiry or account-right changes between initial validation and commit are contained under the final locked session observation. Failed authoritative lookup leaves unknown status or refuses mutation according to the explicit operation contract.
- Company `02` selection still resolves the source catalog in literal company `01`. Relevant duplicates, SQL NULL mappings, case/padding collisions and physical-row replacement invalidate or reject the observation; no client-provided complete-catalog assertion is trusted.
- A read-only balance/replay observation becomes stale when its authoritative mode generation changes. Reading A/B filters versus combined C never implies that Gold/Silver conversion, source clock cutoff or complete `MsAcBal` opening has been proven.
- Real HTTP/database tests verify atomic scope/mode persistence and zero unauthorized writes; a real multi-client browser journey verifies stale-state recovery and accessible status. None of these integration tests has been performed for this prospective seam.

The Windows command classifier, live edition/exception authority and registration/runtime acceptance remain separate unresolved requirements in the frozen Round11 contract and source addendum. The next feasible code change is the persistence/observation boundary once those authorities are explicitly provided; the pure helper alone cannot fill them.
