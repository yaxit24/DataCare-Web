# Independent session-context migration review

The staged SQL and minimal Prisma patch have no remaining confirmed mismatch against the declared baseline after the two preflight corrections described below. This is a source review and a frozen set of proposed verification outcomes. No migration, harness, DB query, compiler, or test runner was executed by this reviewer. The main repository and runtime auth_session remain outside this work.

The independent fixture defines 28 outcomes: four successful compatible states and 24 refusals. Its canonical baseline contains two tenants with the same session UUID, different credential/selected-company scope, active and revoked/expired sessions, a nullable year, and distinct microsecond timestamps. Success cases cover fresh backfill, preserved partial non-NULL values, a maximum BIGINT epoch with a coherent receipt, and validation of a matching new CHECK. Refusal cases cover incompatible type/default/check metadata, invalid epoch/ledger/receipt values, missing or weakened legacy schema, and triggers/rules/inheritance. These are not claimed to exhaust all custom PostgreSQL schemas.

The SQL preserves its complete BEGIN/COMMIT transaction. It requires the existing tenant/session primary key, exact legacy column types, forced RLS and canonical tenant policy. New columns are additive; non-NULL values are retained; only SQL-NULL epoch and ledger values receive the documented defaults. Exact JSONB equality constrains the unknown-only four-key ledger envelope. The receipt is all absent or a complete lowercase UUIDv4/hash/positive older epoch tuple. Native storage cannot reconstruct historical input spelling or duplicate JSON keys; request validation remains a separate layer.

The initial review found that the existing expiry CHECK was not qualified and that backfill could reach user triggers/rules or inheritance children. The final SQL now requires the exact validated expiry CHECK and refuses those table behaviors before adding columns or updating rows. It does not replace legacy constraints, policies, owner, ACLs, indexes, expiry, refresh hashes, or session business fields. Additional custom constraints/policies/indexes are not exhaustively qualified; arbitrary user functions within such extensions remain outside the supported baseline.

The dedicated-database strategy is appropriate for this SQL, which explicitly targets public.auth_session and commits internally. An outer rollback or search_path-only schema isolation would not provide equivalent isolation. The proposed harness creates a uniquely named/commented database on the isolated localhost:55433 server for each case, executes the exact frozen SQL bytes, compares failure schema/data/physical snapshots after process exit, and drops only databases whose ownership receipt matches. Success must preserve legacy values/metadata, retain preexisting non-NULL context fields, verify app_user tenant visibility, and be physically unchanged on a second application. Its snapshot must preserve numeric values as text and distinguish SQL NULL ledger values from JSON null; the reviewed correction does so.

The staged schema fields do not implement context epoch CAS, bearer-token generation checks, refresh/session atomicity, selection recovery, vendor-mode authority, or known ledger closing balances. Integration must coordinate every old/new session writer. Fixture and harness preparation provides no live authorization or desktop runtime parity credit.
