# Saved Return: next numeric commit and known-closing contracts

This is a prospective, source-based implementation handoff. No code, schema, active plan, API, UI or test assertions are changed. No execution acceptance is claimed. The three existing row/bill/labour preview versions retain their read-only authority; the current labour fixture correction is separately pinned. X13 and its original package/variant/33-field acceptance remain open.

## 1. Recommendation and a finite path to a first real commit

The next acceptance target should be **one already saved, canonical, untagged incoming row, changing only Other amount (c27), in an ordinary primary Return with zero tax and no tenders/outgoing/components**. This can become a genuine bounded numeric commit without first implementing every source picker, outgoing variant or known ledger balance. Unknown closing is not a desktop prohibition on all saves: the source save validations use other facts, and no inspected guard requires `CustClAmt` to be known. Known closing is a separate track below.

Do not enable even this narrow commit by serializing the existing preview or calling `editSaleReturn`. Its exact missing prerequisites are finite:

1. A pure source save-field projection and representability check, including source row inclusion and immutable saved identity. This is the immediately implementable core slice; complete it with literal tests as part of the commit work, not as an indefinite replacement for it.
2. A bounded ordinary-Return effect builder which accounts for **every** owned saved/stock/account/tax/rojmel/outstanding/remark side effect for this profile and recognizes the current stored effect set. Whole observed scope membership and external references must be checked before any deletion/update. The c27 event must not silently erase a legacy companion that the builder cannot reconstruct.
3. A Serializable server commit which admits the live authenticated session, matches exact raw/dependency/document versions, replays the accepted journal, applies only the verified write plan atomically and verifies postconditions. The existing transaction helper owns ReadCommitted and the exact readers require RepeatableRead/Serializable; they cannot simply be nested.
4. A strict commit endpoint and real DB/HTTP/UI tests for full effects, old-page/session/version refusal, rollback and unchanged roundtrip. Keep all existing preview endpoints unchanged and all unsupported cases explicitly read-only.

The initial deployment must name its bounded mathematical/PostgreSQL persistence profile and the deliberate raw-preserving web differences below. It does not claim unrestricted desktop Save or full financial parity. A later expansion can admit the other eleven money events, c13/c29 selection commits, multiple rows, tax/tender/header events and source/tag/outgoing workflows only after their complete effect deltas and guards are independently proved.

## 4. Immediately implementable pure save projection

Proposed new core module `saleReturnIncomingSaveProjection.ts`; do not change existing calculator/projection exports. Freeze a complete literal fixture and typed API before implementation.

Input is a strict detached server-internal envelope `{rowIdentity, ordinal, raw, visible}`. `raw` is the exact saved row snapshot; visible contains exactly the63 existing visible source columns, with no caches mixed into it. Ordinal is the existing validated sorted business ordinal. The caller must separately prove the admitted document/profile; the pure function never authenticates a source, master, tenant or state just because fields are present.

Output is `{status:'ready', version, profile, raw, sourceFieldValues, differences, requirements, canCommit:false}` or recoverable unsupported diagnostics plus unchanged raw. `sourceFieldValues` covers only explicit grid-owned SL_DETL_RTN assignments; it is never passed as a complete SQL row. Retain raw NULLs and original numeric/float text independently. Parse Val-owned visible numeric cells only within the existing plain-decimal finite36 significant/18dp/abs<1e36 profile, with blank visible numeric text→0 where the source explicitly calls Val. Missing cells, NULL visible numeric values, controls/newlines, exponents, prefixes and unsupported precision refuse. No Number roundtrip. Canonical mathematical numeric strings are not a promise they can be stored exactly in a Float column.

Report rather than execute these source branches: c12+c38 cancellation would omit the row; visible ordinal differs from persisted SR_NO; c40=0 would allocate an instance; raw identity disagrees with hidden/display source identity. A source tag blank maps to N and data-type blank maps to A, but the first write profile requires stable current stored identity/data type and must not silently apply these defaults to unrelated raw fields. No row, fold, bill, clock allocation, SQL, session update or journal mutation occurs.

The first commit may use the pure projection to identify values affected by its replay. It **preserves unowned raw fields** instead of treating the desktop's every-save resets/defaults as permission to overwrite them. For example raw descriptionNULL must remainNULL if only c27 changes, even when display3 contains the master fallback; original HUID, code, extra scale, source serial, flags and hidden values remain exact. This is a deliberate limited web edit profile; full desktop reserialization is a later contract. A no-event/same-value no-effect commit must not rewrite numeric columns merely to normalize scale, set NULL to0 or change xmin.

## 7. Server commit transaction, staleness and retry

Proposed public request: exact `{documentVersion,baseVersion,rowIdentity,prefixVersion,events}` for the first profile; scope/voucher are retained route/query identity. No raw rows, computed cells/totals, customer/account, ledger mode, policy, table names or save-capable flags accepted. Both page headers mandatory. Body/event limits at least as strict as preview. Route action update, never read. A dry-run/plan token must remain distinguished from a commit authorization.

Use one tenant Serializable transaction with the session row as its first application lock, fresh identity/epoch/unknown-ledger and after-lock SQL expiry check, followed by deterministic document and per-tag/source locks where applicable. Reuse the existing session admission invariants through a behavior-preserving internal Tx seam or a separately versioned write helper; retain current order ReadCommitted and preview fixed-read contracts. Do not nest withTenant transactions or pass the read helper to a writer.

Within that transaction: read all raw header/rows/companions/config/master/guard facts and physical tokens; compare requested base/document/history dependencies **before projection**; validate the complete first-write profile; replay full server-owned ordered prefix from trusted saved hydration; build the complete effect plan; validate expected old effects and incoming/outgoing foreign-reference absence; bind typed SQL values without Number loss; perform exact-row updates/inserts/deletes; verify counts and conservation; recheck exact session identity/epoch/mode and live SQL clock immediately before callback return. No session/JTI/receipt updates while holding SHARE, no LOGIN_MAST row lock after session (password-reset lock order), no auto-retry after scope change.

Serializable can abort on concurrent phantom/reference changes; map40001/P2034 to409 with no claimed save. It does not mean every external raw writer is synchronously blocked or the snapshot is latest-at-response. If strict protection against overlapping nonparticipating configuration/source writers is required, add shared family revision/lock protocol and prove each adopter. No universal in-flight writer promise.

Save success returns freshly observed raw/document version and a new preview baseline requiring explicit editor reset/adoption. It does not keep the old prefix valid or silently merge new data. Empty/ineffective event sequences may return an explicit no-op with no business DML. Repeating a successful changed command with old version must refuse409/no duplicate financial effects. On lost acknowledgment, retain draft and require explicit reload/inspection; do not imply the current session selection receipt proves a financial operation. If automatic exact recovery is required, implement a separately specified durable financial operation receipt keyed by tenant/session/UUID and canonical body digest in the same transaction. That is an optional additional acceptance slice, not a fake reuse of JTI or the single latest context-selection receipt.

Untouched raw text/NULL/full identities must roundtrip exactly. For touched numeric columns, match actual SQL storage schema: pure36-digit decimal acceptance is wider than many numeric(p,s)/Float targets. Reject unsupported rounding/overflow before mutation; bind decimal strings and verify typed stored results. Fields of type Float need an explicit representability policy and real PG cases; `Number.isFinite` alone is not exactness. Saved imported values that remain untouched need no forced Number conversion.

## 8. Known ledger and closing: separate prerequisites

Current code is explicit unknown authority: `sessionContextValue.ts` admits only `server-session-ledger-context-v1/status:unknown/mode:null` with three reasons. A resolver that returns A/B/C internally does not fit that deployed protocol and must not be injected or cast around it.

The required next authority decision is the trusted provider of completed-bootstrap, source edition and exception classification, with revision, tenant/installation binding, refresh/expiry and audit semantics. Do not decode private registration identifiers, choose a hardcoded mode, infer edition from company/book DATA_TYPE, trust browser JSON, or treat a successful login as completed desktop company bootstrap. Reuse the pure sessionLedgerMode proof, including changed command edition without reset; do not reinterpret keyboard bitwise guards as a web authorization policy.

A future known-mode schema/profile must specify: exact complete provenance/history or reference, stable mode revision, permission to issue semantic mode commands, compare-and-swap epoch, operation receipt semantics, current-only recovery and revocation/refresh interactions. Mode change increments contextEpoch even when company/location/year repeat and invalidates open prefixes across tabs. Plan a new additive migration and synchronized runtime/browser DTO version; never rewrite the frozen unknown-only migration or broaden only one parser. Legacy unknown sessions remain valid and explicitly unavailable.

Once that authority is available, add a **new** read-only closing profile using the session RR helper extended under an explicitly new schema version. In the same snapshot:

This can expose known closing while numeric save remains false, or an independently qualified c27 writer can ship while closing stays unavailable.
