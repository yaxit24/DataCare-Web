## Confirmed two-stage loss and existing containment

`getSalesOrder` builds input-shaped values with Number/null-to-zero or trimmed text, then applies `exactOrderValues` to Sales header/parents/children only; `options.orderMainBook !== 'TOUR ORDER'` excludes Tour. The exact helper (`orderLifecyclePolicy.ts145–160`) retains NULL and returns a decimal string only when the already-projected Number differs from the persisted Decimal. The imported parent `ITM_MRP=999999999999999.99` therefore becomes a rounded Number on Tour GET. `preserveOrderRow` at300–308 correctly refuses it, rather than allowing an approximate unchanged save. The same gap affects mapped component Decimal fields from `readStoneSubDetail`126–192, and nullable auxiliary header/parent/component fields.

The form's `hydrateTourOrder` (`tourOrderForm.ts338–361`) already renders values as strings. `SubDetailGrid` displays those supplied strings directly; its own generic `toSubDetailInput` converter is not called by this Tour page. The second loss is `tourOrderPayload`364–425: `numberCell`333 converts every numeric editor value back through Number, and blank text/null become omitted fields. Removing only the API exclusion would still round the exact returned MRP/child value before PUT.

Sales already retains a loaded document and restores unchanged permitted input-shaped values in `salesOrderPayload`365–464 after calling the shared Tour serializer with four arguments. Its field journals and dirty arrays are Sales-specific. Do not import those F1/calculation policies into Tour or change the Sales caller during this correction.

## Proposed bounded implementation

2. Retain a detached loaded DTO with the Tour page's selected voucher/version/scope, clear it on reset and replace it on each authoritative load. Pass it only on saved PUT serialization. New Tour creation and Sales' existing four-argument calls keep the old serializer path.
3. Add an optional original DTO argument to `tourOrderPayload`. Begin with the existing filtered, full-component payload. For supported input fields whose current visible string equals `String(originalValue ?? '')`, restore the exact original scalar, including NULL, zero, blank string and high-precision decimal string. Preserve row/child removal, addition and all current filtering semantics. Require the supplied saved version to match the retained original document version before restoration; no baseline rebase.
4. For a changed saved numeric editor with ordinary decimal syntax, forward its exact text rather than a rounded Number. This is transport preservation, not permission to write it. The existing API `preserveOrderInputRow`162–187 accepts an exact saved string unchanged, computes supported changes as before, and rejects an edited value that cannot be represented by the existing calculation. Continue existing finite-number validation and blank handling. Do not round/truncate a changed huge decimal into a supported one. This correction does not invent a broad new syntax/number parser or source-runtime precision guarantee.
5. Preserve Tour's existing labour commit, cached preview and dirty-field semantics: no new events on hydrate/focus/Tab; do not infer a numeric recalculation from inspection. An unchanged NULL auxiliary field is represented as an empty control and sent back as NULL; an existing numeric zero is visible as `0` and sent as zero. This slice establishes those untouched distinctions. It does not silently change the server's existing explicit-dirty rule for NULL-to-zero or blank writes, nor certify all historical NULL combinations as calculable. A raw NULL in an essential calculation basis may remain unsupported by the writer; no fabricated default is added.

The MRP input and component numeric inputs already bind strings, so no number-typed input conversion is needed. Display-only estimated totals may continue existing number arithmetic; they are not substituted for saved writable scalars or claimed to reproduce every imported aggregate. The complete representative browser fixture must keep calculated bases ordinary and place large/NULL values in supported auxiliary/child fields to prove the requested unchanged/advance-only path without claiming a new numeric calculation profile.
