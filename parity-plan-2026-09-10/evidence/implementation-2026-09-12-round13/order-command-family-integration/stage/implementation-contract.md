Each new required entry detaches the whole input with `structuredClone` before any await, freezes a copied exact scope, fixes its family, and passes that very scope to `withSessionContextCommand`. Old internal Tour/Sales wrappers deliberately retain optional versions; this is an explicit modern-web concurrency improvement, not an old business-rule claim.

Preparation must not introduce a lifecycle object for new create, since that would accidentally remove Sales' required date. ## Lock order and transaction guarantees

The existing command helper uses one ReadCommitted tenant transaction: tenant/isolation validation → exact auth_session FOR SHARE → after-lock SQL live/context check → plain fresh principal/stored scope/form reads → financial callback → final full identity/epoch/ledger/live check → commit. It neither updates the session nor retries. Create rights remain View-based; edit needs View+Edit and cancel needs View+Delete. Missing session authority has no compatibility branch on participating HTTP handlers. Prehandler checks do not cancel transactions already past admission.

Create callback order is: plain configured BOOK_DATA read (`salesOrder.ts802`) → Sales fiscal read if applicable804 → plain labour settings805 → source resolution/calculation → full-scope voucher advisory lock (`numbering.ts148–155`) → plain maximum from configured live header tables → hidden-number advisory lock across tenant/company/location/book (`lifecycle.ts40–56`) → TEMP insert → posting balance/period read (`posting.ts510–512`) → header, parents, all children, Rojmel and ledger inserts → exact imported/clock restoration. The full-scope voucher lock precedes hidden-number lock; hidden identity intentionally omits year. A new Tx seam retains both and never uses a counter outside the transaction. The source MAX rule permits highest-deleted number reuse; no request idempotency or gap-free sequence guarantee is added.

Edit/cancel callback order is: plain book → per-voucher advisory lock (`salesOrder.ts1326–1332`) → saved header FOR UPDATE (`lifecycle.ts121–129`) → all-table version and policy observation → unsupported state/child restrictions → persisted/new dates' period reads as before → consumed/issued/tagged detail check (`salesOrder.ts1573–1594`) → complete delete/replacement or reverse. Edit reuses saved voucher/hidden identities and does not allocate new numbers. Cancel does not take number-allocation locks; this preserves existing top-delete/create race behavior. A create racing deletion may observe the still-live highest number and allocate the next one, or observe committed deletion and reuse the deleted maximum. Neither order promises which voucher number wins across an uncoordinated delete/create schedule.

No newly inspected Tx callee requests an auth_session or LOGIN_MAST lock after order locks. Selection and refresh take the conflicting session UPDATE lock first; password reset takes LOGIN_MAST then session UPDATE. Authority reads remain plain MVCC reads to avoid the reset LOGIN→session / command session→LOGIN cycle. Do not call these lifecycle coordinators inside financial callbacks or upgrade the command's SHARE lock. Multiple financial commands may hold SHARE simultaneously; existing per-document locks/versioning and number locks remain essential. Two creates with valid context and no intervening deletion use one book's allocation lock and can both commit distinct numbers. Two mutations on one saved version yield one committed mutation and a stale/not-found domain refusal for the other, depending on whether the winner edits or deletes.

There is no identified new lock-order blocker for these five routes under the inspected standard schema. This is not universal deadlock freedom: other writers, multi-session resets, database triggers/custom constraints, settings changes from other sessions, and unconverted adjustment/consumption writers retain their own behavior. Session exclusion does not freeze CO_SET/USER_SET globally. Final expiry enforcement is at the helper's final SQL statement, not an exact COMMIT-time clock proof. Known rollback removes the entire financial set; an ambiguous COMMIT response or lost HTTP success must not be automatically replayed.
