# Independent review of the next saved Return writer contract

The finite c27-only saved incoming commit is a sound next implementation direction, with the mandatory stock identity correction below and explicit post-replay admission. This review does not approve a DML endpoint from the current partial candidates. The original contract itself correctly requires a complete source-derived before/after effect fixture and a new transaction boundary before implementation. The pure save-field projection can proceed after its own complete literal fixture is frozen; existing read-only preview permission is not write permission.

The reviewed original contract remains byte-identical (`ffb358067fff21f5921fd7edd66e2e1638fe28cc2fc48735211805a198274f24`), as do all 33 candidates and the 64-assignment source map. The separate reference comparison confirms all 44 pinned inputs still match; it is a hash check, not a claim to have independently read every line of all 44 files. ## Mandatory correction and admission clarification

1. **Stock identity is `SR_NO=2`, `ISR_NO=incoming.SR_NO`.** The phrase `SR_REC_ISU2` in section 6 is incorrect. `Ac_Stock.cs:247` explicitly inserts 49 named columns, beginning scope/voucher, `SR_NO`, `ISR_NO`, then dates and metadata. Its corresponding values are `A.VCH_NO,2,A.SR_NO`. `TR_TYPE='I'`, `ITM_SIGN='+'`, `ITM_QTY=1`; `DATA_TYPE=A.DATA_TYPE`. The incoming stock row is not identified by the return line serial in both columns. Current Prisma `MAIN_STOCK` has no `SR_REC_ISU` field (`schema.prisma:3855–3914`). The mandatory erratum JSON includes all 49 source column/expression pairs, avoiding an abbreviated identity mapping becoming the new implementation template. Account postings separately use book `B.DATA_TYPE` (`Ac_Ledr.cs:1324,1326`); neither is session ledger mode.

2. **Validate the bounded profile again on the replayed final state.** Saved incoming-only eligibility and a c27 event allowlist do not prove that the resulting document remains an incoming credit, includes its row, or passes Save's amount guard. Under the intended plain P1 branch (metal100 + labour10, no MRP/discount/tax), c27=-110 gives row0 and rounded bill0; the ordinary Save amount guard refuses. c27=-120 gives row net -10, and source inclusion `Val(c12)+Val(c38)!=0` becomes `10-10=0`, omitting the row. c27=-200 gives row -90 and `BILL_TOTAL` switches to received90. The first writer excludes these outcomes and must refuse before DML, unless separately expanded to all their guards/effects. Sources: `TR_SALE_RTN.cs:5075–5081,12376–12403,14252,16385–16419`. These numbers are conditional source branch examples, not results from the incomplete P1 JSON or an executed reducer. The additive review cases preserve that qualification.

## Candidate precision and the immediate work boundary

W01/W03/W04 figures follow the intended simple branch and the source account/stock expressions. W02 is specifically a *no-effect* web policy case, not permission to skip the actual same-valued event. P1 is intentionally partial: it does not pin all visible fields, eight caches, item/type agreement, LBR_TYPE, MRP/tag price/discount values, full settings/widths, or stored effects. In particular, `CommPassTotal_Pr` can change other price/tag/cache fields on c27; its MRP branch can replace totals independently (`TR_SALE_RTN.cs:4866–5158`). Before making W01/W02 executable writer goldens, freeze complete raw/projection/configuration/effect rows and prove that the permitted journal changes only the owned persistence fields. A successful mathematical calculation is not sufficient evidence of a storage-exact change plan.

All 64 map entries match their cited `dataRow5` assignment lines exactly (separate `assignment-comparison.json`). The map is correctly labeled an index rather than a complete SQL row. Its contextual assignments (`VCH_TIME`, `MAIN_USER`, `EMP_CODE`) and conditional defaults must not be accidentally treated as visible-column expressions. `SR_NO←c0`, `OLD_SRNO←c51`, `RATE_TYPE←c44`, `TAG_TYPE←c54`, `IT_TYPE←c43`, the blank-tag/default-data-type branches and instance allocation agree with source. The raw-preserving web policy deliberately avoids reserializing NULL description from the displayed master fallback or normalizing untouched identity/clock/default fields. P01–P09 are consistent with that named policy; they are not a claim that every broader VB `Val` input is implemented.

Freeze exact target storage for every touched field. Return row OTH/TOT/NET and stock OTH/NET are numeric(18,2), whereas header RTN_NET/RTN_TOT/RTN_BILL_OS are Float (`schema.prisma:5643–5735,5867–5960,3855–3914`). The proposed arbitrary-precision arithmetic domain alone cannot authorize a Float roundtrip. `MAIN_STOCK.ENTRY_TIME` is currently a date although source supplies incoming `VCH_TIME`; an unchanged edit must retain its raw stored value, and any new effect insertion must explicitly qualify the target representation. Preserve physical rows on a true no-op; comparing formatted display text alone cannot establish one.

## Effect and save-guard findings

- Source bill/history sequencing is correctly separated: the row calculator invokes fold then bill (`TR_SALE_RTN.cs:5157–5158`); Save invokes both folds without an explicit Bill call (`12376–12383`). W04 correctly retains per-row110.01 versus header/bill110 under the intended branch. Do not add an inferred roundoff account leg merely to make unrelated representations equal.
- `Ac_Ledr.cs:1324,1326` creates customer CR and group SALE_AC DR from each incoming `NET_AMT`, with blank SIGN, reciprocal LD_CODE, and different PARTY_AC_CODE values. Exact LEDR_KEY source expressions include `STR(A.SR_NO)`; the full golden must pin the source-compatible representation, not substitute a generic unpadded JavaScript string. The other ledger legs are gated by outgoing/tax/tender/UAE/fine conditions through line1395. Unknown actual membership or relevant ambiguous joins must refuse before changing an existing effect.
- The tax warning and W06 are correct: non-UAE `Ac_Tax.cs:191,193` inserts TAX_DATA for matching SR1/SR2 tax masters and nonzero RTN_NET even with tax0. The AC_GST_TYPE predicate is `<> 'I'`, so SQL NULL is not equivalent to canonical N. W06 assumes its two qualifying canonical master rows; it does not prove a universal two-row count. Source metadata and row multiplicity must be literal fixtures.
- Rojmel must be derived independently, including `BOOK_DETL` membership/cardinality, BOOK_TYPE, and `A.VCH_DATE >= MOp_dt` (`Ac_Rojmel.cs:586–616`). The RTN_BILL_OS credit and BOOK_TYPE T RTN_NET debit summary are distinct rows. Their account/description/key and date predicates cannot be recovered from a balanced AC_DATA total.
- W07 is correct: `TR_SALE_RTN.cs:13194–13225` deletes the scoped outstanding set for non00045 but inserts only when received total r3c4 is nonzero. A payment-side credit outstanding is not justification for a received BILL_OS_DATA row. An unexplained existing outstanding or allocation must block this narrow writer.
- Zero new cash does **not** by itself make the cash-limit guard inert. `TR_SALE_RTN.cs:12149–12171` can call `LedrCash` whenever MsCashLimit>0 and account!=00045, then compare prior AcCash plus current received cash. The planned builder must resolve this guard or prove a configured zero limit; it must not use unavailable closing as a substitute. Defaulter received-OS, employee, counter, period and rights guards remain separately qualified. The special fine/registration branches can only be bypassed when proven inert for the exact poststate, or resolved by trusted classification.
- Global NULL-maintenance statements in desktop helpers and destructive reserialization are not part of the scoped effect contract. Existing generic `editSaleReturn` deletes a fixed write set and calls Number-based create (`salesReturn.ts:743–802`); it is correctly excluded as the implementation of this primary saved numeric writer.

## Session, staleness and closing boundaries

The transaction plan is consistent with current helpers: command admission is ReadCommitted, read admission is RepeatableRead, both retain session SHARE and perform after-lock/final SQL liveness/context checks (`sessionContextCommand.ts:211–366`, `sessionContextReadSnapshot.ts:200–354`). A new Serializable writer must own one transaction with fixed Update authority, keep the session-first lock order, avoid a later LOGIN_MAST lock, and match versions before projection. Preserve original errors for ambiguous transport/commit failure; a serialization refusal is not a safe reason to silently retry under a new context. T01–T06 describe required schedules, not executed proofs. Full-table/reference preservation and audit accounting must be asserted separately.

L01–L07 and M01–M04 retain the correct source/authority separation. `DC_Main.cs:1463–1487` initializes six balances, uses strict-before and inclusive cutoff queries across books, sums CR-DR before aggregation, and converts amount plus both metals. Grouped NULL is not a no-group zero. `TR_SALE_RTN.cs:16424–16455` calculates bill closing from opening plus payment OS minus received OS, retains prior color at zero, and does not reuse the helper inclusive close as the event result. Current unknown-only session persistence cannot be widened by a caller-supplied A/B/C mode. Bootstrap and later alias commands in `MS_OPNCOMP.cs:1459–1475` and `MDI_FORM.cs:12721–12790` support the literal distinctions, not a new vendor authority provider.

A c27 writer can remain closing-unavailable when all its own save/effect guards are independently qualified. A known closing profile may remain read-only. Neither grants the other permission. The next concrete release gate is the complete, storage-qualified P1 before/after effect fixture plus post-replay admission and Serializable writer tests; this review is not acceptance of that implementation or of the wider X13 requirements.
