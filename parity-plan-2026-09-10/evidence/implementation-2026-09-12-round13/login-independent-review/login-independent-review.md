# Internal login coordinator: bounded independent review

The staged coordinator rechecks its private, successfully verified credential observation under a LOGIN_MAST row lock before creating a session. It compares exact row identity, password, password-change timestamp and reset flag. It then resolves scope and fresh principal, inserts epoch1 with an explicitly unknown ledger context, signs locally and checks exact persisted expiry again before commit. LOGIN_MAST precedes auth_session in this path, matching the existing reset/change lock order. No ordinary-path defect was confirmed in this read.

Critical source points: `sessionContextLogin.ts`24–27 exact credential lookup; 47–66 private verification/hash preparation; 69–86 locked recheck and legacy update; 88–96 scope/fresh detached principal; 97–122 unknown context and168-hour session; 124–138 local signing/final expiry. `passwordAccount.ts`108–147 resets the credential before revoking matching active sessions. `businessScope.ts` private company/location/year helpers retain current selection/default semantics; login still intentionally allows no configured year. `authorization.ts`65–86 returns the credential-owner company in principal, distinct from the immutable session login company. Prisma LOGIN_MAST3772–3788 retains varchar1 flags and a nonunique identity index.

Root expressly approved two new web behaviors beyond the historical login matrix: existing duplicate credential identities are refused, and a legacy password upgrade rolls back together with session insertion when scope/signing/transaction work fails. This review does not silently attribute those changes to the old implementation.

The new test file stages13 real-database cases: complete configured login and168-hour interval; absent year/SQL NULL; modern forced reset and fresh rights; committed legacy upgrade; modern and legacy signer rollback; wrong, missing and duplicate credential refusals; legacy rollback on missing requested year; signing across expiry; a credential change committed between verification and locked recheck; and actual resetUserPassword waiting behind the login lock, then revoking both the newly committed and prior target session while preserving another company and tenant.

Fixtures use schema-admitted varchar1 flags. Full row text plus xmin/ctid snapshots keep SQL numeric and timestamp representations outside JavaScript Number/Date parsing. The initial/final clock override uses exact millisecond fixture instants; the expiry comparison itself is SQL. The first race applies a deliberately held credential fixture update, not an invocation of the whole reset writer. The second race invokes the real reset service. Both wait for actual PostgreSQL lock observations, release holds and settle started promises. Signers return local test strings: these tests do not validate JWT signatures, cookies or HTTP routing.

Known limit: the LOGIN_MAST identity index is nonunique. LIMIT2 detects duplicates visible at each read, but the current row lock does not prevent a concurrent imported duplicate insertion. Root accepted this as an unqualified concurrent-import boundary and will decide coherent identity admission before full endpoint rollout. No identity-uniqueness or universal credential-import concurrency acceptance is claimed. No-op internal audit callbacks do not establish future route auditing. No known ledger mode, balance resolver, last-day-lock trigger or scope epoch endpoint integration is introduced here.
