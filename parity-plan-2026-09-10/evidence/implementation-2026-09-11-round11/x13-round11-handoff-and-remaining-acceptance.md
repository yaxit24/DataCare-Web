## What the new slice provides

Round11 adds a separately versioned saved incoming Return bill preview alongside the existing v1 single-row preview. The public routes are GET `/sales-returns/:vchNo/incoming-bill-replay-state` and POST `/sales-returns/:vchNo/incoming-bill-replay`; the POST is a read simulation under the Return form's View right. It observes one explicit tenant/company/location/year/configured Return book and exact positive five-digit saved voucher key. Other imported key shapes remain outside this initial profile.

The pure header projection separates exact raw data from source-loaded F2 controls, the cleared9×6 bill matrix and full-incoming/tax comparison caches. The composed service observes all incoming rows, configuration, source-relevant item masters, tax settings and tax/bank/card display-master rows in the same RepeatableRead transaction. Its new token binds the observed physical versions and semantic versions before row/header projection. It does not relabel the old v1 token as an aggregate token.

The phases are distinct: saved raw; loaded header and row displays without recalculation; incoming running aggregate followed by the final supported incoming-only saved-open bill callback; then one selected row's ordered explicit committed-cell events, with required aggregate and bill callbacks between events. An unsupported sibling is not dropped from the sum. A failing event does not publish its transient row or downstream totals over the last complete prefix.

Only source columns19,20,21,23,24,25,26,27,28,36,37,38 are admitted by this preview. The server supplies row identity/ordinal, policy and effective source widths. Clients cannot supply gross/fine bases, F1/source copies, header/tender amounts, tax policy, ledger mode, opening balance, caches or phases. Same-value genuine events remain ordered events; this is not a final-values recalculation API.

The UI separates saved, opened and preview amounts, retains rejected text, and requires reload after a stale observation. Its new exclusive row/bill preview ownership must also prevent metadata editing while a preview is active. API, UI and real-browser proof are credited only through root's final current-input results; this note itself adds no runtime evidence. The separate `x13-bill-projection-core-run.json` records the pure projection's84 focused tests and strict compiler result only.

## Smallest coherent next balance prerequisite

Resolve the ownership of session `MsDataType` before implementing a closing capability. Source `MS_OPNCOMP:1459–1475` and `MDI_FORM:12726–12790` distinguish this session mode from selected-book posting `ItmDataType`; the current session has no established authoritative mode property. Do not add a client flag defaulting toC or borrow the book's DATA_TYPE to make the balance appear complete. Name the fresh web policy and version any authoritative mode/configuration observation. If no such authority is available, retain the existing unavailable closing state while other independently known outputs remain inspectable.

Once that prerequisite is explicit, implement a transaction-local ledger observer, not a new posting path. Source `TR_SALE_RTN:10197` calls `DC_Main.MsAcBal`; `DC_Main:1463–1487` uses exact saved customer and company/location/year across all books. Opening is strict-before the source date plus clock truncated to seconds; helper closing is at-or-before. ModeC includes all data types, other supported modes use the exact source filter. Do not add same-voucher exclusion, selected-book restriction, VCH_DATE filtering or per-leg COALESCE not present in the source.

Required discriminators include another-book eligible entry; equal-second and later-microsecond entries; foreign tenant/company/location/year/account; NULL ENTRY_TIME; absent eligible groups versus present all-NULL sums; mixed NULL/non-NULL debit/credit; and source-relevant GoldWt/SilverWt conversions as well as amount. The Round10 addendum explains why a finite money sum alone does not prove the original helper completes when metal sums are NULL. If only amount arithmetic is implemented, label it a partial amount observation and do not claim complete saved-open helper parity.

Bind relevant physical ledger/mode observations to the new response/token within the same snapshot. Verify a consistent as-of-start result under actual interleaving and a stale token on the subsequent request. State the limitation of present-row xmin/ctid evidence: an absent→insert→delete cycle is not durable history unless a separate persistent revision owner is added. Keep unknown clock/mode/precision explicit; never turn it into a fabricated0 balance.

Before any numeric writer is enabled, freeze the complete event/admission and write-set contract for the actual source mode. Reuse the existing pure kernel, projection and resolved settings, but replay inside the full locked/Serializable transaction with exact saved/source identities and all effects. Read tokens alone cannot authorize stock consumption or detect every phantom history.

At minimum, complete source F1/code-copy field order and caches, original sale availability and OLD_SRNO child ownership, noncontiguous identity preservation, both incoming/outgoing table families, tag/stock/karigar valuation, header RTN_* effects, tender/refund/credit allocation, source edit/delete conflicts and exact permitted reversal. No default conversion of raw NULL/blank/large decimals, wholesale isuRef removal or generic Sales writer reuse is an acceptable shortcut.
