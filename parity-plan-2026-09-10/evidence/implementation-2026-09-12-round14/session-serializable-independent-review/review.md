## Transaction and authority

The fixed interface accepts only the five-field scope policy, not caller form/action/admin overrides (`sessionContextSerializableCommand.ts:146–178`). Identity and scope are descriptor-copied before the first await (61–183,304–316), including contained reflection failures. The strict scope addendum deliberately bounds printable ASCII, whitespace and database widths; it does not change existing helpers or desktop parsing. Numeric/leading-zero/overflow epochs refuse without coercion. The retained identity can have its own undefined year, but the complete command refuses that state before SQL.

One `withTenant` call explicitly requests Serializable (319–389). `tenant.ts:23–26` binds RLS through transaction-local set_config; the new helper verifies the actual binding and isolation (323–334). The first application-row lock is the exact tenant/session `FOR SHARE` (335–342), before principal, scope or form reads. Tenant setup and the settings query are not application-row locks, but may already establish the snapshot.

Subject identity is checked before the post-lock live query, then epoch/business context and the exact unknown-ledger envelope are checked (196–239,343–354). The separate `clock_timestamp()` query is issued after the locking statement returns, avoiding a clock sampled before a lock wait. The admission passes a detached/frozen context, principal, rights and form authorization to the same transaction callback (356–384).

Current `loadPrincipalTx` still gives priority to the selected credential company, while the immutable authentication company remains `context.loginCoCode` (`authorization.ts:65–86`). `validateStoredScopeTx` checks the exact selected company/location/year without choosing a new default (`businessScope.ts:133–150`). The fixed authorization uses `Sales/Sales Return` and `update` (375–383). Existing semantics are retained: non-admin Update requires View and Edit; administrators retain the existing bypass; USER_SET lookup remains LC_CODE/USER_NAME/form alias with its existing first-row ordering, not a newly invented company policy (`authorization.ts:119–162`).

After callback success, the final query rechecks full retained subject/scope/epoch/unknown-ledger/revocation and SQL expiry before allowing return (241–268,384–386). The callback value reaches the caller only after `withTenant` has successfully committed. Rechecking same-snapshot data sees the transaction's own writes, so controlled local epoch/ledger misuse is detectable. It is not a general auth-DML sandbox: the contract forbids callback auth/JTI/receipt writes, LOGIN locks, nested transactions and external effects, while the TypeScript Tx can still express prohibited SQL. Do not claim the two misuse tests prove arbitrary auth fields cannot be changed by a malicious callback.

The coordinator itself has SELECT-only application SQL, no session mutation or rotation, and no retry. Known raw40001/40P01, P2034 and P2010 meta40001/40P01 map once to409 (271–279,402). ScopeError retains its actual code/status, missing principal becomes401 and form denial becomes403 with update context (390–403). Unknown callback, connection and COMMIT acknowledgment errors propagate; this does not establish their transaction outcome or make a retry safe.

## Lock order and snapshot limits

The existing RC command and RR reader files match their frozen hashes. Their API/behavior was not altered. RC intentionally sees a committed session winner after waiting; the new Serializable helper, like the RR reader, may instead get a serialization failure if an UPDATE commits after snapshot creation. It does not refresh/rebase identity or retry that command.

Selection locks auth_session before its transactional reads/last-day lock; refresh also locks auth_session; logout UPDATE conflicts with SHARE. Password reset acquires LOGIN_MAST before updating auth_session (`passwordAccount.ts:108–132`). The new helper never adds a LOGIN row lock after SHARE. That avoids the direct session→LOGIN versus LOGIN→session lock inversion for the reviewed callback schedules. A future callback must retain this restriction and define its own subsequent document/effect lock order.

Serializable supplies a consistent snapshot and SSI conflict detection, not latest-at-response authority. A nonparticipating rights/config writer can commit after that snapshot while this command succeeds; D05/D12 explicitly exercise that bound. It also does not synchronously block every phantom. The final live check is the final SQL statement's clock boundary, not a claim that expiry was sampled at the later physical COMMIT instant. Session SHARE excludes cooperating concurrent session writes until commit; it does not cancel already-running financial work or every unrelated writer.

`coBook` is validated/detached policy text, but is not checked for configured membership or included in the admitted context DTO. D10 even uses company02 while the fixture's R13 book exists only under01. That is consistent with this helper's deliberately limited contract, not a valid Return document admission. The eventual adopter must synchronously detach its complete business request, bind its consumed scope to this policy, and validate the exact Return book/document/profile and complete dependencies within this same transaction. It must not close over a different mutable request scope.
