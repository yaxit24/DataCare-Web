## Generated review registers

`form-register.json`, `grid-requirements.json`, `control-requirements.json`, `event-requirements.json`, `report-register.json`, `table-register.json`, `settings-review.json`, `report-slugs.json` and `register-summary.json` are generated by `../build_registers.py` from the frozen source measurements and retained mapping. They deliberately label requirement and certification status unverified.

The grid records enumerate 3,508 named header occurrences. Forty-three have no direct-literal source-line match in the simple line finder; their source file/grid/header remains available for manual resolution. Header ordinals are not a substitute for actual desktop column indices. Event/control declarations and source lines identify investigation locations, not proven behaviour. Decompiler artifacts, dynamic labels and conditional code need interpretation.

The settings alias index detects property dereferences outside the loader; it is a candidate data-flow aid. It does not resolve arbitrary aliases, destructuring, runtime dispatch or every false name match. Both this index and the raw scanner require real setting-effect tests.

The report register checks file existence now but retains older binding candidates as labelled historical metadata. Verify current bindings in code and through the report contract. The 20 absent references must be resolved rather than assumed to be mandatory templates or harmless dead references.

## Reproduce without overwriting this snapshot

Run `../capture_measurements.py --output /absolute/path/to/a/new-snapshot`. The command requires a directory that does not already exist, reruns source extractors, connects dependent measurements to the newly generated JSON in memory, and records the measurement-script hashes. It does not run databases, browser journeys, migration, provider calls or deployments.

`../build_registers.py` regenerates the review registers in this plan directory from its current evidence and the current mapped source. Preserve this delivered directory before intentionally regenerating it. A new implementation snapshot should have its own date/build identity and a reviewed comparison to this one.

The plan's acceptance requirements are normative work to perform. The evidence here is only what was actually observed during planning. Neither the existence of a register nor a passing ratchet proves production parity.
