# End-to-end implementation plan

## Target and operating rules

Deliver the complete web replacement for the supported DataCareNext desktop product: the same business operations, fields, defaults, calculations, validations, decisions, document relationships, stock/money effects, reports, printing and practical operator efficiency. Preserve the existing web investment where it meets that contract. This is a behaviour-preserving migration, not a bulk relabelling exercise.

**Full-product parity is the default target of this request.** Here, “in scope” means every reachable capability of the agreed primary desktop version, including supported country/book variants and companion functions it relies on. Historical waivers, low usage, missing extraction, absent web pages and engineering difficulty do not reduce that scope. A later explicitly narrowed deployment may be certified only for its declared subset; it cannot be called the complete desktop replacement. A source-backed proof that a duplicate/compiler artifact has no distinct business effect is a disposition, not a feature exclusion.

The 83 packages are delivery containers, not a fixed ceiling on requirements or tests. Complete the discovery inside them, create additional child requirements/tasks for every newly found behaviour, and keep each parent open until its descendants and cross-module acceptance obligations pass. The [re-verification report](08-plan-reverification.md) and [additional source register](09-additional-source-register.md) are mandatory inputs. No statement in this plan certifies the current application or guarantees that implementation will succeed without those measurements.

“Production for generic jewellery businesses” means configuration and data variation are supported: different charts of accounts and book codes, branches, years, products, rates, labour methods, stock policies, settlement methods, printers and roles. An implementation that only reproduces one demo company's records is insufficient.

Keep two explicit lanes. **Desktop compatibility** preserves source-confirmed business semantics. **Web production improvements** add concurrency handling, session isolation, safe retries, observability, responsive usability, accessible controls and recoverability. When they alter visible desktop behaviour, document the difference and obtain business acceptance. Do not reproduce an unsafe implementation detail merely because the desktop uses it, and do not silently change a financial rule while improving the implementation.

All work begins from the reviewed working tree, not a reset to HEAD. Inventory and preserve current modifications. Use an isolated development/test environment; existing business databases are not test fixtures. This plan does not authorize production migration or actual customer/provider communications.

## A requirement is complete only when its entire path works

For every form field and action, record:

| Contract element | Required detail |
| --- | --- |
| Identity | Stable requirement ID; source form; grid/control or action; desktop version/hash |
| Visibility | Edition, country, book, user, company-setting and workflow-state conditions |
| Input | Type, length, scale, signedness, units, enumeration, default and blank/null/zero distinction |
| Lookup | Dataset, scope/filter, sort/search, picker columns, default selection and dependent fills |
| Calculation | Trigger event, formula, order, rounding point, override precedence and downstream effects |
| Validation | Condition, operator message, focus destination, blocking versus confirmable behaviour |
| Persistence | Request field; route adapter; domain input; write column; source references; full ownership key |
| Reading/editing | Reader and hydration mapping; identity preservation; untouched-value preservation |
| Effects | Ledger, Rojmel, stock, tax, outstanding, allocation, image, audit and printing effects |
| Branches and callers | Menu/constructor/book/state/role/setting entry conditions; helper, timer and asynchronous callers; state transition and error/confirmation alternatives |
| Continuity and history | Required network/service mode; historical-record behaviour; offline/retry/upgrade effects; permitted technical differences |
| Proof | Golden vectors, API/DB/browser tests, desktop capture, exact differences and operator acceptance |

An occurrence in TypeScript, an API accepting a field, or a generated input box satisfies none of the later steps by itself. Computed fields need visible accurate results and round-trip protection; hidden/internal fields need preserved server identity, not editable inputs.

## P00 — Establish trustworthy scope and evidence

### P00-01 — Freeze and reconcile the complete product inventory

Preserve the current dirty tree, executable/source hashes, dependency lockfile, schema/migration version and existing evidence. Reconcile 204 source units, 198 menu entries, 101 web route files, 255 report binaries, 20 additional report references, 146 table units and the initializer/restored-schema counts. Parse `MDI_FORM.cs` menu handlers, constructor parameters, book classifications and runtime menu data. Resolve the 12 unresolved menu labels and inspect mismatched mappings such as loan issue/receipt rather than trusting their names.

Reconcile the whole primary assembly tree, not just the `DataCareNext/` namespace directory: it has 212 C# files, including eight support files outside the original 204-unit register. Include entry point, settings/resources, referenced DLLs, database routines, installer/configuration dependencies and companion invocations. Merge the 916 additional modifier-bearing input declarations in the supplemental register with the original 1,599 candidates, retaining provenance and deduplicating semantic identities. Resolve the 43 named-grid records without a literal line match. Neither 2,515 combined declaration candidates nor the original field ratio is a semantic completion denominator.

Output a canonical inventory with stable IDs, category, variant parameters, current web destinations, explicit missing/partial/unverified status, ownership and dependencies. Keep one form mapped to several routes and several forms mapped to one route visible. **Accept when every source/menu/report/data item has a disposition and the source totals reconcile; no new waiver is inferred from a previous narrative.**

### P00-02 — Capture the desktop as an independent reference

Prepare an isolated Windows installation with the correct executable, dependencies, Crystal runtime, fonts, permissions, settings and sanitised databases. Preserve the installer and hashes. Observe each business mode; capture input actions, prompts, intermediate totals, output documents and before/after database state. Existing SQL Server exports of real records prove historical stored results, but do not by themselves prove the user action sequence or application version that produced them.

Create desktop cases for create, unchanged edit, changed edit, cancellation/deletion, import/adjustment and print. Include at least two unrelated business configurations and two branches/years for scope-sensitive operations. **Accept when captures are reproducible and attributable to an executable, configuration, fixture and operator/run; synthetic fixtures used to test the differ are separately labelled.**

### P00-03 — Replace misleading completion metrics

Repair scanners to recognize typed setting aliases, actual `recalcLine` use, quoted/unquoted report registry keys, dynamic masters, conditional grids and wrapper props. Replace global field-name matching with page → route → writer/reader mapping. Discover all grid pages before applying the dead-cell audit; an unmapped page is a failing coverage obligation. Validate the scanners with positive and negative controls, including an unused field with the same name on a different page.

Validate declaration modifiers, inherited/resource-created controls and supported third-party control types against independent source samples. In particular, `MS_PRINT` has three `private virtual CheckBox` declarations although the original scanner counted zero inputs. Extract async/non-void methods, delegated actions and call sites; a regex event list is only a starting index. Compare parsed control trees to rendered desktop forms and actual event wiring. Inventory disagreements fail coverage rather than being normalized into a smaller denominator.

Keep old scanner numbers for historical comparison but introduce requirement coverage, transition coverage, field-path coverage, configuration effect coverage and independently matching cases as separate measures. **Accept when deliberate broken controls fail for the intended reason, shared variants remain distinct and no dashboard calls a count ratio “functional parity.”**

### P00-04 — Create a real full-stack verification environment

Provision fresh PostgreSQL from migrations, force RLS, create non-owner runtime credentials and seed isolated test businesses. Run real API and web services with matching build identifiers. Retain the existing stubbed browser tests for interaction feedback, and add a separate authenticated suite that uses real requests and inspects resulting rows. Enumerate dynamic master names and report slugs, not only one sample per dynamic route.

Keep test fixtures independent of the demo/live tenant, enforce UTC in deterministic arithmetic tests, and add explicit India/local-time business-date tests. **Accept when every required route can be exercised with valid context, auth failures are distinguishable from render failures, and DB tests cannot pass by skipping.**

### P00-05 — Make contracts and CI enforce coverage

Extend the existing 11 authored contracts using the form register. Each field/action gets the contract elements above; each conditional branch gets a test or a source-backed not-applicable disposition. Fill missing formula vectors through source interpretation and desktop runs. A debt ratchet that accepts unresolved draft rules remains an engineering guard, not a release gate.

Create a versioned requirement graph from product → capability → form/mode → action/field/decision → request/reader/writer → tables/reports/provider effects → case evidence. Enumerate business decisions inside handlers, constructors, startup/shutdown, timers, context menus, shared engines and error/retry paths. Each leaf has an owner and exact work-item/test links; each source item has a reviewed disposition. Test source-dead claims across callers and configurations. No package closes on a declaration count, a sample contract or passing tests for only one caller of a shared helper. New discoveries expand the graph and reopen affected parent acceptance.

Move/register web build and release workflows under the actual repository-root `.github/workflows/`, with correct working directories. Verify the required checks are active in the hosting repository and attach retained evidence through approved artifact retrieval. **Accept when a PR with a deliberately omitted required contract/test fails and the actual CI system runs the checks.**

## P01 — Compatibility kernel and transaction integrity

### P01-01 — Formalize identity and scope for every table family

Use tenant + company + location + fiscal year + book + voucher number as the logical voucher scope, with table-specific exceptions documented explicitly. Preserve zero padding, spaces, hidden voucher identities, line serials, tag-instance serials and reference keys. Follow `vouchers/numbering.ts`, `vouchers/lifecycle.ts` and `posting/posting.ts`; audit every read, mutation and report query for complete keys.

Desktop `LEDR_KEY` layouts differ by family and sometimes by leg within one voucher. Catalogue them rather than using one universal string concatenation. Treat HUIDs, account codes and identifiers as text. **Accept on two-company/two-location/two-year fixtures sharing book/voucher/tag numbers, with no cross-scope reads, writes or images and exact persisted identity comparison.**

### P01-02 — Complete numerical policies and precedence

For every desktop formula, identify whether it uses formatting, `Math.Round` or another conversion; capture negative midpoints, per-line versus voucher rounding, rates per gram/ten grams/kilogram/piece, fine and net bases, wastage, ghat, stone conversion and customer/karigar valuations. Preserve blank versus explicit zero and distinguish operator overrides from derived values.

Use `packages/core/src/money.ts`, `finePolicy.ts`, `shared/roundingPolicy*`, `labourDesktop.ts` and related helpers where they match the measured contract. Replace local arithmetic only after vectors establish the required policy. **Accept when source-cited vectors match the desktop at every rounding boundary and preview/API/persisted values agree; no blanket epsilon adjustment or arbitrary tolerance is allowed.**

### P01-03 — Close complete posting footprints

For each family, enumerate header/detail/subdetail, `AC_DATA`, `ROJ_MEL_DATA`, `MAIN_STOCK`, tax, outstanding, order/booking/member adjustments, tender identity, image and audit writes. Measure row counts and semantic role codes by book. A balanced ledger alone is insufficient: a balanced voucher can omit both sides or write the wrong accounts. Rojmel is a movement view, not a ledger mirror; signed metal rows and unsigned money rows have different meaning.

Keep configured book-account resolution fail-closed; remove unmeasured fallback account/leg assumptions through contracts. Reconcile the retained 510 field differences and missing/extra rows one classified defect at a time. **Accept when the full allowed write set matches desktop evidence, other tables do not change, and downstream stock, outstanding and reports reconcile.**

### P01-04 — Standardize create/open/edit/delete and correction transitions

Define which families permit saved-but-not-effected state, direct posting, reversal, deletion, controlled correction and dependent-document locks. Preserve observed business states even when implementation makes the transaction atomic. Use `postVoucherTx`/lifecycle helpers for period checks, numbering and complete reversal. Do not replace a separate `UT_USER_REQUEST` workflow with an invented mandatory reason on every delete.

Require row/version or equivalent stale-edit detection, documented read/modify semantics and preserved immutable reference identities. Test unchanged reopen/save using distinct rich values, then edit one field, add/remove/reorder child rows and delete. **Accept when unchanged business values remain unchanged, permitted audits are explicit, dependent documents remain valid, and unauthorized/locked transitions have zero partial effects.**

### P01-05 — Make concurrent writes and retries deterministic

Specify uniqueness and transaction locks for voucher allocation, live tag consumption, book sequence, order balances, outstanding settlement and booking drawdown. Add idempotency for user-initiated mutations that may be retried after a lost response. A retry must return the original result; conflicting payload reuse must be rejected. Keep external sends after committed state with durable attempt identities.

Run overlapping sales of one tag, two payments against one bill, simultaneous source allocation, edit-versus-delete and request timeout immediately after commit. **Accept when no duplicate voucher/payment exists, balances cannot be overconsumed, the losing operator receives an actionable conflict and rollback/retry leaves no orphan row.**

## P02 — Shared form richness, interaction and settings

Build a reference screen with main lines, two distinct subdetail sets, source allocation, dual valuation and editable payment/received totals. **Accept when its full desktop contract can be represented and tested without hiding domain logic in arbitrary field-name conventions.**

### P02-02 — Complete child-grid editing and calculation

Extend `SubDetailGrid.tsx` and `shared/stoneSubDetail.ts` with per-form columns and calculations. Cover diamond/certificate data, pieces and piece weight, conversion, amount, labour, net amount, customer valuation, karigar valuation, component return/breakage and old issue references. Match field names (`lbrRate` versus `labourRate`, for example) through the actual writer. There are 38 retained IDTL grids across 35 forms; validate that inventory against source.

Keep stable child identity under row insertion, removal and sorting; distinguish source/return component sets. Recompute or preserve overrides exactly as desktop does. **Accept with two parents having dissimilar children, reorder/delete/copy tests, complete save/read/edit preservation, correct totals and cross-parent isolation.**

### P02-03 — Implement cell-exit, lookup and totals behaviour

Trace the 416 desktop grid event sites into functional behaviours. Adopt recalculation only on applicable forms; do not require meaningless hooks on header-only screens. Implement lookup fill chains, current-row item/photo/balance panels, automatic touch/rate/slab selection and reset of dependent fields. Create an editable totals/settlement component with the desktop's row-oriented tax, discount, TCS/TDS or round-off, cash/cheque/card/UPI, advance, old-gold, scheme, kasar and outstanding cells.

Keep manual override flags explicit; changing an upstream field must recompute derived values without accidentally freezing a previous preview as an override. **Accept when tabbing, picking, pasting and editing yield the same intermediate and final numbers as the source contract and server.**

### P02-04 — Complete keyboard and high-volume operator ergonomics

Audit F1–F12, modifier shortcuts, Enter/Tab/arrows, row append/delete, Escape, save/print/new and modal focus. F6 is present; F10 requires desktop observation because a caption alone is insufficient. Preserve the effect of row-change/search preferences required by current scope. Support full grids with clear grouping, fixed identity/totals columns, column visibility preferences and readable amounts/weights.

Test primary workflows keyboard-only, barcode scanning into the correct focus, lookup cancel, empty row removal, validation focus and conflict recovery. Add accessible labels/error associations and useful 1366×768, larger-counter and tablet layouts. **Accept when experienced operators can complete the benchmark without hidden required fields, trapped focus or materially worse throughput.**

Include the desktop's practical use of multiple open forms: consult a ledger or master while preserving an unfinished invoice, return to the same row/selection, compare two documents and open a related record. Implement equivalent tab/window navigation without leaking company/book context or stale defaults. Distinguish per-user, per-device and per-form preferences; test session/context change with several tabs open. Do not demand the old Windows window chrome, but preserve the operator's task and information density.

### P02-05 — Implement settings as observable business policies

For all 130 inventory rows and configuration in `CO_MAST`, `TAG_SET`, books, users and window settings, record table/key, exact default, allowed values, load/consumer paths and all affected forms. Deduplicate registry keys by table/key rather than spelling alone. Prioritize money/stock/validation settings, then workflow/printing, then interaction preferences. Verify the typed alias effects already present before adding code.

Examples still requiring consumers or further proof include `BRANCH_ALL_AC_SHOW`, `DUP_PRINT`, `CUR_DAY_POSTING`, `SL_TAG_WT_DIFF`, lot stock, estimate locks/tax, weight/fine locks, silver precision and image-print switches. `CUR_DAY_POSTING` governs stock refresh scope; it must not be implemented as a guessed date restriction. `SL_TAG_WT_DIFF` changes stock reconciliation, not merely sale permission.

**Accept with table-driven allowed-value/default/invalid tests plus real persisted outcome tests for each business branch. A loader read or disabled UI input is not enough; direct requests must obey the same policy.**

### P02-06 — Complete form session and error behaviour

Keep draft values through recoverable errors and session refresh; warn before navigation discards meaningful work. Resolve company/year/book changes explicitly and clear dependent state safely. Show server validation at the relevant field/row and preserve the failed values. Prevent double submit, identify successful saves after uncertain network responses and avoid accidental duplicate printing or messaging on retry.

Make internet-independent operation an explicit P00 architecture decision and R10/R11 release obligation. Distinguish internet outage, LAN loss, server failure and device-bridge failure. A browser served by a local/LAN application and database can preserve shop posting during an internet outage; a cloud-only deployment ordinarily cannot. If disconnected browser posting is required, specify its local store, access control, document identities, reserved stock/number ownership, stale rates/permissions, synchronization, conflicts, reconciliation and restart recovery before implementation. Do not select a local server or offline synchronization solely from this plan without validating the intended topology.

The user's full operational-parity target remains open until ordinary desktop-independent sales, stock, settlement, lookup and printing can continue under the agreed outage conditions, or the user explicitly accepts a narrower operating service. Such a limitation must appear in the release claim. Cached pages or saved drafts alone do not prove offline business operation. Online provider actions retain their actual connectivity requirement and visible pending/failed states.

**Accept with a documented service-mode decision and expired-session, internet/LAN/server disconnect, reload, back-navigation, local persistence/reconnect and retry tests for that mode; no silent data loss, conflicting accepted stock, duplicate posting or ambiguous posted status.**

Measure correctness, task time, keystrokes, re-entry, lookup success, print quality and recovery from mistakes. Verify configuration-specific behaviours with more than one representative shop.

**Accept signed UAT for every in-scope business journey and report, no necessary desktop fallback and no substantial counter-efficiency regression. Cosmetic modernization is accepted separately from business equivalence.**

Maintain a behavioural difference register: expected desktop result, observed web result, reason, affected requirements/data, risks, independent review and compensating acceptance tests. Separate a proven technical representation mapping from a business deviation. An approved security/provider/statutory change can be the correct production decision but must be disclosed as a deliberate difference; it is not evidence of literal behavioural identity. Missing functionality, lost offline service, absent reports or untested branches cannot be reclassified as cosmetic modernization.

### P14-04 — Rehearse cutover and rollback on a production-like target

Freeze a source snapshot, perform the final shadow load, reconcile, deploy the candidate, configure peripherals/providers, run smoke journeys, and practice the rollback decision. Define source-of-truth ownership during the transition, delta handling between snapshot and switch, duplicate-entry prevention and handling of new web transactions if a rollback is needed.

**Accept a timed rehearsal, reconciled opening balances/stock/outstanding, usable recovered desktop/archive, tested communications and a precise go/no-go checklist. After web writes begin, rollback must reconcile/replay them; restoring an old backup would lose accepted business.**

### P14-05 — Perform controlled business rollout and stabilization

Start with a representative business/branch only after its entire required scope is certified. Compare daily closing totals, stock, fine balances, allocations, provider statuses and prints during the agreed observation window. Expand only after acceptance. Keep a named support owner, defect response process, reconciliation schedule and rollback authority.

**Accept completion when all intended businesses/configurations are covered, normal and exception workflows operate without unplanned manual work, recovery targets are proven, and the business owner accepts the handover. A technically successful deployment alone is not completion.**

### P14-06 — Retire contradictory progress claims

Update the canonical completion register, contract statuses, current handoff, journal and release notes with verified evidence. Preserve old audits as dated history; mark them superseded where facts changed. Separate implemented, engineering-verified, desktop-compared, business-accepted and production-certified states. Include the remaining whole-product exclusions, if any, in the product's supported-scope documentation.

**Accept one navigable current record that another engineer or business owner can audit without relying on this conversation. No “100%” claim may coexist with an in-scope contained, absent, skipped or unverified workflow.**

## Execution discipline and change review

Each work package is delivered as a reviewable vertical slice: approved desktop contract → required schema/API/UI/report changes → focused regression and failure tests → desktop differential → business demo → evidence/status update. Small UI wiring changes need meaningful field-path/round-trip verification rather than a new test that merely repeats a property name.

The first implementation sprint should complete P00-01 through P00-04 and fix the P10-01 report binding/scope defects, while finalizing P01 contracts for identity and lifecycle. Then use purchase/tag opening and a rich sales/return case as reference slices before propagating shared UI changes. This order validates the method on financially meaningful examples before scaling it to every source unit.

Review numerical and write-footprint changes with an engineer who did not author the implementation and a domain operator/accountant for business semantics. Test evidence must show that negative controls fail for the intended reason. If a fixture, scanner or baseline changes, distinguish the measurement change from a product improvement.

Never close a requirement using an arbitrary minimum page count, a minimum count of validation messages, 100% API field-name occurrence, a DB-column write count, a screenshot of a populated form or a balanced trial balance alone. The closure target is **all applicable requirements and transitions verified**, regardless of how many components/routes implement them.
