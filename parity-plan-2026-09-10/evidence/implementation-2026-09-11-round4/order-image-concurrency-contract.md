# Saved order photo concurrency — round 4

This implements the same-photo conflict/retry descendant explicitly left open in round 3. It is a web concurrency addition for multiple operators. It is not claimed as an independently executed desktop behavior or as historical image migration completion.

`ENTITY_IMAGE_REVISION` retains a BIGINT revision for tenant/company/branch/entity/key/instance even when the image bytes are removed. The migration preserves the image store's installed company/branch widths and instance representation; it does not shrink, relabel or rewrite historical image identities. Existing identities start at revision zero until their first application mutation. The new table has forced tenant RLS and is discovered by the existing company backup schema manifest.

All current application image writers (`saveEntityImage`, `deleteEntityImage`, and `changeOrderImage`) first create/lock the shared revision identity inside the same transaction as the bytes and TAG index mutation, then advance its revision. The image lock covers an absent image and is shared across different saved order parents and orders. A failed validation/transaction rolls back the revision as well as the bytes/index. Deleting and recreating identical bytes still invalidates an earlier token.

Saved-order GET returns an opaque token combining the saved parent identity, revisions of all candidate images, a hash of the raw stored bytes/metadata and the exact tag-index state. The raw fingerprint additionally detects changed imported or corrupt bytes that did not pass through an application writer. Photo mutations compare that token after acquiring the image locks. If the photo or saved identity changed, the route returns its existing 422 diagnostic and requires an explicit reload. The browser keeps the operator's context, shows the conflict, and exposes Reload image followed by an intentional retry. No automatic retry overwrites an unseen photo.

The generic image endpoints retain their earlier request contract; their writes advance revisions and invalidate saved-order clients. Those generic editors do not yet require their own optimistic request token. Out-of-band restore/import requires its operational maintenance barrier; this addition does not make concurrent raw database replacement safe or claim provider/device acceptance.

Focused database evidence is `image-revision-focused.txt`: 3 files and 34 tests passed, including 11 saved-order image tests. Added cases verify stale replace/delete rejection, absent-image delete/recreate, two independently locked orders competing for one TAG image, generic editor invalidation with identical restored bytes, and forced tenant isolation. The company backup regression includes an image revision above JavaScript's safe integer range and verifies its exact serialized value. Final full-suite/browser results are recorded by the round-4 root checkpoint, after the combined implementation is ready.

`image-conflict.journey.mjs` exercises the real browser against a second actual request client: a newer photo is saved, the stale operator upload fails and preserves the newer bytes, Reload displays that photo, and an explicit retry succeeds. It replaces no HTTP responses. Historical image transfer, physical cameras/printers, shared Design Book edit acceptance, and production-scale image performance remain separate open requirements.
