## Implemented behavior

The new saved-header projection preserves the exact raw header, initializes the source nine-by-six bill matrix and its comparison caches, and distinguishes direct numeric reads from the four source Fnv fields. Only `KASAR_AMT`, `BILL_OS`, `RTN_KASAR_AMT` and `RTN_BILL_OS` accept their source NULL/blank-to-zero path. Missing, NULL or unsupported direct numeric fields produce diagnostics and an unavailable phase. Saved tax and payment values remain visible without being overwritten by current master values or calculations.

The new authenticated GET `/sales-returns/:vchNo/incoming-bill-replay-state` and read-only POST `/sales-returns/:vchNo/incoming-bill-replay` use the owning Sales Return View permission. Both return `no-store`. A single RepeatableRead transaction observes the complete scoped saved document, every incoming row, the existing row configuration, qualified company tax settings, and tax/bank/card display masters. Exact physical revisions and alias observations participate in a separate bill token. A stale token is refused before row projection or replay. Clients provide only that token, an opaque saved-row identity, and an ordered list of original field-change events; totals, tax policy, modes and caches remain server-owned.

Saved, loaded and opened states have distinct meanings. The loaded phase performs source header assignments without recalculating item rows. The opened phase folds all incoming rows in their explicit source order and invokes the bill callback with the source empty outgoing-grid total. It never substitutes the saved outgoing header amount for a missing outgoing grid. Every accepted numeric event replays the selected row, folds the entire grid, and recalculates the bill in that order. A failure in any stage retains the last complete row, aggregate and bill prefix. Other rows remain part of the calculation and keep their saved identities and values.

One independently authored case starts with incoming rows110 and50, saved manual tax7, and saved payment total166.75. Opening displays incoming160, tax7 and payment167. Changing the first row's Other amount to1 produces incoming161, tax16.10 and payment177. Returning Other to0 produces incoming160, tax16 and payment176. The previous tax-cache transition makes the final bill different from its opening state even though the final item amounts match. The implementation preserves that history instead of calculating only from the final row values.

The web adds a separate **Totals and bill preview** within Saved returns. It shows exact saved amounts, fourteen incoming totals, payment/received amounts on opening and after committed changes, source labels, the selected row's saved and preview values, and the ordered journal. NULL, blank and unavailable values have different displays. Only the twelve existing source-qualified numeric fields are admitted. Explicit button/Enter commits preserve repeated events and deliberate blanks; Tab does not commit. Invalid drafts and previous previews remain visible. Conflict recovery requires an explicit saved reload followed by an explicit fresh preview.

The row-only and totals/bill panels have mutually exclusive ownership. Both synchronously acknowledge the parent's activation claim before opening or dispatching a request. Active previews freeze metadata editing, document replacement and local book selection. A closed or superseded asynchronous request cannot restore a prior document through an A→B→A book change. The old row-only API contract, calculation helper and existing journey assertions remain intact; its component has only the bounded activation-acknowledgment change needed by the shared parent.
