## Authenticated context lifecycle implemented in this round

`sessionContextSelection.ts` locks the exact tenant/session in one Serializable transaction. It validates the current bearer, exact scope, positive string epoch, live expiry and fresh rights before recognizing the one stored receipt. Fresh selections resolve target scope and principal, refuse target password-reset requirements, apply last-day-lock under ordered setting-row locks, locally sign the successor token, and atomically update scope/epoch/unknown-ledger/receipt. A fresh same-scope open increments once. Exact receipt recovery requires the current bearer and original UUID/body/epoch, revalidates the stored scope, and does not update the session or settings. HTTP auditing still appends one expected entry. There is no automatic transaction retry or unlimited receipt history. Stale bearer E cannot recover committed E+1.

`sessionContextRefresh.ts` uses ReadCommitted and locks the session before classifying exact expiry and JTI reuse. Strict reused-refresh revocation commits even when later principal/context data would be invalid. A valid refresh preserves exact scope, context epoch, unknown-ledger observation, receipt and absolute expiry; it reloads current permissions, signs both tokens before rotation, and checks expiry again in the update. Lost-response retries and concurrent tabs retain the existing strict reuse/revocation behavior; no grace window was invented.

`sessionContextLogin.ts` revalidates an exact locked credential after password verification. Legacy hash upgrades, scope resolution, new epoch1 session insertion and token signing share one transaction. SQL establishes a 168-hour absolute lifetime. A password reset before credential-lock admission refuses login; a reset waiting behind successful login sees and revokes the new session. Duplicate observed credential identities refuse admission. The existing nonunique identity index still does not prevent a concurrent importer inserting a new duplicate after the lookup; that limitation remains open.

`sessionContextAccess.ts`, JWT and the HTTP handlers require canonical epoch claims and exact live persisted session identity. Old access tokens without an epoch receive401; a valid refresh can issue the new contract. `/me`, login, refresh and selection return a five-field context descriptor plus explicit unknown ledger context and no-store headers. The browser sends both session-ID and epoch headers; partial or mismatched pairs receive409. Both headers absent remain allowed for compatibility/bootstrap. These checks occur at request admission and do not yet hold a session lock through every business transaction.

The browser page guard captures the exact descriptor for requests, refreshes, binary downloads and device callbacks. Different refresh authority makes the old page stale; it cannot silently re-label or retry a retained draft. Company selection stores its original UUID/body/epoch in sessionStorage before dispatch. Uncertain outcomes preserve the draft and freeze ordinary requests until explicit navigation to the recovery screen. Recovery uses fresh `/me` and the exact original operation, with distinct retry and accept-current choices. Successful selection invalidates old responses before full navigation. Local operation leases prevent a late login/password/selection response from navigating after its component or route has left; Shell releases the departed route's local busy state while retaining recovery data. Physical WebSerial hardware and loopback bridge behavior are not certified by callback-double tests.

The original last-day-lock forward-only behavior and login trigger boundary remain explicit desktop differences. Target-company password-reset refusal is an explicit web authority/recovery improvement. Ledger mode remains unknown; no A/B/C defaults, customer closing or financial preview persistence were enabled.
