# Parity Gap Analysis — FINANCE + LOANS (DHRN) + KEY REPORTS

Group: `gap_finance_loans`. Generated by deep read of decompiled C# WinForms in
`extracted_code/DataCareNext/DataCareNext/` vs web rebuild in `web/apps/api/src/modules/{finance,dhrn,accounting,reports}` + `web/apps/web/app/(app)/txn/*` and `/reports/*`.

Method: read actual `.cs` SAVE handlers, computation methods, and `INSERT/UPDATE` SQL. Citations are `File.cs:line / method`.

---

## 0. Core architecture the web does NOT replicate

Desktop posting is **table-derived, not code-derived**. Every transaction form writes its own
*source* table (e.g. `CASH_DATA`), then **re-derives** the ledger and day-book by calling shared
helpers that re-read the source table:

- `Ac_Ledr.Cash_Ledr / Bank_Ledr / Sale_Ledr / ...` → builds `AC_DATA` (double-entry ledger)
- `Ac_Rojmel.Cash_Rojmel / Bank_Rojmel / ...` → builds `ROJ_MEL_DATA` (rojmel = day-book / cash-mel)
- `Ac_Tax.Vch_Remark(book, vchNo, type)` → writes voucher remark/narration rows
- Save pattern is **DELETE-then-INSERT** per voucher across ALL derived tables, so edits are idempotent.

The web (`finance.ts`, `dhrn.ts`) instead hand-writes a 2–3 line `AC_DATA` ledger inline and writes a
single header row. It does **NOT** write `ROJ_MEL_DATA` at all, does **NOT** call any shared posting
helper, and does **NOT** use the DELETE-then-INSERT idempotent re-save. This means the web day-book
(rojmel) report can never match desktop, and edits are unsupported.

## 1. FINANCE — Cash / Bank Receipt & Payment (desktop `TR_CASH.cs`, 3849 lines)

ONE desktop form (`TR_CASH`) serves **four** books via `FormMainBook`: `CASH REC`, `CASH PAY`,
`BANK REC`, `BANK PAY`. It is a **multi-line MSFlexGrid** (`MSG`) voucher: one voucher = many party
lines. Web splits this into separate `receipt`/`payment`/`contra` single-line endpoints.

### Save workflow — `BtnSave_Click` (TR_CASH.cs:2877)
1. **Validations (all missing in web):**
   - Licence expiry block on new entry (`MsSoftNoUse`).
   - Employee code mandatory if `MsEmpCodeMendetry='Y'` (`tEmpCode`).
   - **Per-party cash limit**: loops grid, calls `DC_Main.LedrCash(acCode, book, vch)` to get the
     party's *accumulated* ledger cash, then blocks if `lineAmt + AcCash > MsCashLimit` (TR_CASH.cs:2914).
     Web only has a single static PAN-over-200k check (`assertCashLimit`) — different rule entirely.
   - Company type `B` cannot save (TR_CASH.cs:2930).
   - Voucher date must be within company open/close date (`MCo_OpDate`/`MCo_ClDate`) (TR_CASH.cs:2939).
   - **Lock date** block: `MsLockDt >= vchDate` (TR_CASH.cs:2946).
   - User edit-rights check (`UsUPdate`/`UserEdit`/`EntryMode`) (TR_CASH.cs:2952).
   - Voucher-no present check; on Add, **re-checks MAX(VCH_NO) collision** and bumps if taken (TR_CASH.cs:2964).
2. `MSG_TOT_FILL()` totals the grid.
3. **DELETE-then-INSERT** for the voucher across: `CASH_DATA`, `APR_IDTL`, `TEMP_BOOK_DATA` (header book row).
4. Insert header into `TEMP_BOOK_DATA` (BOOK_NAME, HD_VCH_NO link).
5. Loop grid rows → insert each into **`CASH_DATA`** with columns:
   `SR_NO, AC_CODE, AC_NAME, REC_AMT, BANK_CHARGES, KASAR_AMT, IT_DESC, CHQ_NO, CLR_DATE,
   CHQ_PRINT_NAME, BANK_NAME, VCH_TIME, HD_VCH_NO, EMP_CODE, INOUT_TYPE, ENTRY_TYPE='C',
   VCH_TYPE(=FormBookSname), DATA_TRFR, RE_TRFR, MAIN_USER, USER_UPDATE, USER_DELETE`.
6. `DELETE AC_DATA` for voucher → re-post via `Ac_Ledr.Bank_Ledr` (BANK REC/PAY) or `Ac_Ledr.Cash_Ledr`.
7. `DELETE ROJ_MEL_DATA` → re-post via `Ac_Rojmel.Bank_Rojmel` / `Cash_Rojmel`.
8. `Ac_Tax.Vch_Remark(book, vch, 3)` → narration rows.
9. `WappReport()` — WhatsApp/SMS the party a "payment received/paid" message (TR_CASH.cs:3151).
10. Recompute party opening/closing balance (`DC_Main.MsAcBal`), print voucher (`BtnPrint_Click`).

### Per-line columns the desktop captures and web drops
`BANK_CHARGES` (bank charges), `KASAR_AMT` (round-off / discount write-off), `CHQ_NO`, `CLR_DATE`
(cheque clearing date — drives bank reconciliation), `CHQ_PRINT_NAME`, `BANK_NAME`, `IT_DESC`
(narration), `EMP_CODE`, `DATA_TRFR`/`RE_TRFR` (inter-location transfer flags), `HD_VCH_NO`
(header voucher link).

### Web implementation (`finance.ts`)
- `postReceipt`: writes single `CASH_DATA` row (REC_AMT, AC_CODE, REC_AC_CODE, CHQ_NO, VCH_DATE) +
  inline 2-line `AC_DATA` (Dr cash/bank, Cr party). No grid, no KASAR, no bank charges, no CLR_DATE,
  no ROJ_MEL_DATA, no TEMP_BOOK_DATA, no remark, no employee, no per-party limit, no lock date.
- `postPayment`: writes **`PAY_DATA`** (NOT `CASH_DATA`) — schema divergence; desktop payment is
  also `CASH_DATA` with `INOUT_TYPE`. Web invents columns NET_AMT/TOT_AMT/CASH_AMT/CHQ_AMT/CARD_AMT/BANK_AC.
- `postContra`: writes **`CONTRA_DATA`** — appears to be a **web invention** (verify; desktop contra is
  a CASH/BANK book entry, not a separate table). Web SR_NO=1, DR_AMT/CR_AMT both = amount.
- `deleteFinance`: reverses header + AC_DATA, writes `DELETE_DATA`. Desktop `BtnDelete_Click`
  (TR_CASH.cs:3200) writes a much richer `DELETE_DATA` (BOOK_NAME, VCH_VAL_DR/CR, FINE_TYPE,
  VCH_FINE_DR/CR, HD_VCH_NO, VCH_DESC, DELETE_USER, times) and also deletes AC_DATA + ROJ_MEL_DATA.

## 2. LOANS — Dhrn/Loan ISSUE (desktop `TR_DHRN_ISU.cs`, 6895 lines)

ONE form serves "DHIRAN ISSUE" (pledge loan out) and "LOAN REC" (loan receivable) via `FormMainBook`.
It is a **pledged-collateral register with a multi-line item grid** (MSG) + per-item photo capture.

### Save — `BtnSave_Click` (TR_DHRN_ISU.cs:5083). Writes **8 tables** (DELETE-then-INSERT each):
1. `TEMP_BOOK_DATA` — header book row (HD_VCH_NO link).
2. **`DHRN_ISU_DATA`** (header) — far wider than web. Columns include:
   `DHRN_BILL, DHRN_DUE_DATE, TO_DATE, AC_CODE, AC_NAME, LEDR_ACCD, LOAN_TYPE, PACKET_NO,
   DHRN_AMT, DHRN_REC_AMT, DHRN_MONTH, INT_MONTH, INT_DAYS, INT_PRC, INT_AMT, INT_REC_AMT,
   OTH_AMT, MONTH_INT_AMT, GOLD_DESC, GOLD_AMT, GOLD_WT, GOLD_NWT, SILVER_NWT,
   OLD_ISU_NO/OLD_ISU_YRCD/OLD_ISU_DBCD/OLD_ITEM_ADJ (renewal/rollover linkage),
   ISU_REC (lifecycle flag), EMP_CODE, VCH_DESC, ENTRY_TYPE (L=loan / D=dhrn)`.
3. **`DHRN_ISU_DETL`** (pledged-item packets, one row per grid line) — the **entire collateral register**:
   `PACKET_NO, CUST_NAME, IT_CODE, IT_NAME, ITM_PCS, ITM_GWT, ITM_OTH_WT, ITM_NWT, ITM_TOUCH,
   ITM_WEST_PRC, ITM_FINE, ITM_RATE, ITM_AMT, NET_AMT, IT_DESC, RATE_TYPE, IT_TYPE, PACKET_REC,
   DHRN_NO/DHRN_YRCD/DHRN_DBCD (links to source issue on renewal)`.
4. `AC_DATA` via `Ac_Ledr.DhrnIsu_Ledr` / `Loan_Rec_Ledr`.
5. `ROJ_MEL_DATA` via `Ac_Rojmel.DhrnIsu_RojMel` / `Loan_Rec_RojMel`.
6. **`DHRN_DATA`** (movement/aggregate table) via `Ac_Tax.DhrrnIsu_Data` / `Loan_Rec_Data` — this is the
   table the OS report + interest accrual read (SUM of INT_AMT, INT_REC_AMT, DHRN_REC_AMT, UNCHAK_DHRN_REC).
7. **`MAIN_STOCK`** via `Ac_Stock.Dhrn_Isu_Stk` / `Loan_Rec_Stk` — pledged gold enters **stock custody**.
8. **`IMAGE_DATA` / `AC_IMAGE`** via `DhirnImgPrint()` — stores a **photo of each pledged packet** (BLOB).

### Special features (all missing in web)
- **Renewal/rollover** of an existing loan (OLD_ISU_NO, OLD_ITEM_ADJ='Y', carries item detail forward).
- **`ISU_REC` lifecycle**: `UPDATE DHRN_ISU_DATA SET ISU_REC='Y'` when fully repaid (join via DETL); reset to 'N' on delete.
- Multi-item pledged collateral with full weight/touch/fine/rate breakdown; `GOLD_DESC` auto-composed.
- Due date / TO_DATE, LOAN_TYPE, INT_MONTH, INT_DAYS, OTH_AMT (other charges).
- Per-packet **image capture**; loan terms WhatsApp message (with custom expiry/interest clauses per `SSRegSrNo`).
- Employee code, lock-date / open-close-date / user-rights validations (same family as TR_CASH).
- Delete (TR_DHRN_ISU.cs:5510) writes full `DELETE_DATA`, resets ISU_REC, removes DHRN_DATA/AC_DATA/ROJ_MEL_DATA/MAIN_STOCK.

### Web `issueDhrn` (`dhrn.ts`)
Writes ONLY `DHRN_ISU_DATA` (header: DHRN_AMT, INT_PRC, MONTH_INT_AMT, GOLD_AMT, GOLD_WT, TO_DATE) +
inline 2-line `AC_DATA` (Dr DHRN / Cr CASH). **Drops**: DHRN_ISU_DETL (all itemized collateral!),
DHRN_DATA (movement table that OS report needs), ROJ_MEL_DATA, MAIN_STOCK custody, IMAGE_DATA,
ISU_REC lifecycle, renewal linkage, due date, loan type, employee, packets, photos, WhatsApp.
Frontend `dhrn-issue/page.tsx` collects only borrower/principal/intPrc/goldWt/goldAmt/dates — no item grid.

## 3. LOANS — Dhrn/Loan RECEIPT / repayment (desktop `TR_DHRN_REC.cs`, 8063 lines)

### Interest auto-computation (TR_DHRN_REC.cs:6960) — THE authoritative formula
```
nIntAmt = Round( PandingDhrn(outstanding principal) * (INT_PRC/100) / MsIntYearDays * nIntDays , dp )
```
i.e. **Interest = OutstandingPrincipal × (INT_PRC/100) × Days ÷ MsIntYearDays** (day-count).
Days are first converted to whole months: `IntMonth = Round(daysBetween(from,to)/365*360/30)` then
**`nIntDays = IntMonth × 30`** (TR_DHRN_REC.cs:6988). So interest is charged on whole-month buckets.
`MsIntYearDays` is a **company-global setting** (so INT_PRC is annual if MsIntYearDays≈360, or monthly
if MsIntYearDays≈30). Matches the accrual in `RP_DHRN_OS.cs:2053`:
`(DHRN_AMT − DHRN_REC_AMT) × INT_PRC/100 × num(days) ÷ MsIntYearDays`.

### Save — `BtnSave_Click` (TR_DHRN_REC.cs:6049). Writes `DHRN_REC_DATA` + posts 4 derived tables.
`DHRN_REC_DATA` columns include: `ISU_NO/ISU_YRCD/ISU_DBCD` (links to issue), `DHRN_REC_AMT`
(principal repaid), `INT_AMT` (interest due), `INT_REC_AMT` (interest received), `INT_PRC`,
**`UNCHAK_DHRN_REC`** (advance / "unchecked" dhrn receipt), **`PAN_ADJ_AMT`** (pending-interest adj),
`MONTH_INT_AMT`, INT_DAYS, dates.
Then (DHIRAN REC path):
- `Ac_Ledr.DhrnRec_Ledr` → `AC_DATA` (Dr cash | Cr loan principal | Cr interest income).
- `Ac_Rojmel.DhrnRec_RojMel` → `ROJ_MEL_DATA`.
- `Ac_Tax.DhrnRec_Data` → **`DHRN_DATA`** (movement/aggregate that OS report sums).
- `Ac_Stock.Dhrn_Rec_Stk` → **`MAIN_STOCK`** (releases pledged collateral from custody).
- `UPDATE DHRN_ISU_DATA SET ISU_REC='Y'` when the issue is fully repaid (join via ISU_NO) (TR_DHRN_REC.cs:6300).
- `Ac_Tax.Vch_Remark(...,0)`.
(LOAN ISU alt path uses `Loan_Isu_Ledr/RojMel/Data/Stk`.) Delete (6365) writes full `DELETE_DATA` and resets ISU_REC='N'.

### Web `receiveDhrn` (`dhrn.ts`) — gaps
- **Interest is NOT auto-computed** — it is a caller-supplied `interest` field; `dhrn-receipt/page.tsx`
  makes the user **type** interest + intPrc manually. Desktop derives it from dates × rate × outstanding.
- Web hardcodes `DEFAULT_YEAR_DAYS=360`; desktop uses configurable `MsIntYearDays` (and whole-month bucketing).
- Outstanding = `DHRN_AMT − Σ DHRN_REC_DATA.DHRN_REC_AMT` (web) vs desktop sums the `DHRN_DATA` table
  (INT_AMT, INT_REC_AMT, DHRN_REC_AMT, **UNCHAK_DHRN_REC** advance) — web ignores advances entirely.
- Writes only `DHRN_REC_DATA` + inline AC_DATA. **Drops**: DHRN_DATA movement, ROJ_MEL_DATA,
  MAIN_STOCK collateral release, ISU_REC lifecycle close, UNCHAK_DHRN_REC, PAN_ADJ_AMT, validations.

## 3b. LOANS — Interest-only receipt (desktop `TR_DHRN_INTREC.cs`, 6576 lines)
Dedicated form to collect **interest only** (no principal) on an open loan — writes `DHRN_REC_DATA`

(TR_DHRN_INTREC.cs:5349). **No web equivalent at all** — the web has no interest-only collection flow.

## 4. KEY REPORTS

### Cross-cutting gap: AC_DATA & ROJ_MEL_DATA are DUAL money+metal ledgers
Desktop `AC_DATA` rows carry, besides DR_AMT/CR_AMT: **`FINE_WT, IT_TYPE ('G'/'S'), SIGN ('+'/'-'),
FINE_RATE`** (seen in `Ac_Ledr` INSERT schema and `TR_CASH.cs:2702`:
`SUM(CASE WHEN IT_TYPE='G' THEN ±FINE_WT) AS GoldWt, ...AS SilverWt`). So every desktop ledger/
trial-balance/day-book is **tri-columnar: Amount + Gold-fine + Silver-fine**. `ROJ_MEL_DATA` adds full
item metrics `ITM_PCS, ITM_GWT, ITM_NWT, ITM_TOUCH, ITM_WEST, ITM_FINE, ITM_RATE, ITM_AMT, LBR_RATE,
LBR_AMT, OTH_AMT, NET_AMT, IT_CODE, MEMB_CODE, SCHM_CODE`.
**Web `posting.ts`/`accounting.ts` only handle DR_AMT/CR_AMT money** — gold/silver fine columns are
dropped everywhere. This breaks ledger, trial balance, day-book, and party-statement parity for a
jewellery business (metal balances are as important as cash).

### 4a. Party Ledger — desktop `RP_LEDR.cs` (11814 lines) vs web `accounting.accountLedger`
- Desktop: opening balance `Σ(CR_AMT−DR_AMT)` before period, running ledger, **+ gold/silver fine
  running balances**, voucher drill-down grid (`dGV_VCH` → fetch source voucher), LC_CODE (branch)
  and book filters, party-group selection.
- Web: money-only opening + running balance (SQL window). **No metal columns, no voucher drill-down,
  no branch filter.** Functional for cash accounts; wrong for metal/party accounts.

### 4b. Rojmel / Day-book — desktop `RP_ROJMEL.cs` (5856 lines) vs web `reports.dayBook`
- Desktop reads **`ROJ_MEL_DATA`** (the dedicated day-book): book-wise (`BOOK_NAME`/`MAIN_BOOK`)
  cash receipts/payments **and metal in/out**, joins `MAIN_STOCK` for **closing stock** Gwt/Nwt/Fine
  by IT_TYPE on the date (RP_ROJMEL.cs:1892), opening/closing cash + metal, receipt summary by AC_CODE
  (RP_ROJMEL.cs:2186).
- Web `dayBook` reads **AC_DATA** money only (Dr/Cr list + totals). **No ROJ_MEL_DATA, no metal flows,
  no closing-stock line, no book grouping, no opening/closing.** Cannot match the desktop rojmel.

### 4c. Stock register — desktop `RP_STOCK.cs` (6407) & Tag stock `RP_TAG.cs` (10813) vs web `stock.onHand`/`reports.stockValuation`
- Desktop on-hand = **`MAIN_STOCK` netted by `ITM_SIGN` (+in/−out)**: `GROUP BY TAG_NO,VCH_SRNO HAVING
  SUM(±VCH_SRNO) > 0` (RP_TAG.cs:8092/9820) — a tag is in stock only if its signed movements net > 0.
  Excludes `APR ISU` / `SALES ORDER` books (consignment/quote, not owned). Design-wise/item-wise/
  date-wise registers, duplicate-tag detection (RP_TAG.cs:3218).
- Web `stockValuation` reads **`BAR_DETL`** (tag master) with `NOT EXISTS(MAIN_STOCK ITM_SIGN='-')` —
  a simpler "sold?" flag, not sign-netting; does not exclude APR/order books, no VCH_SRNO logic,
  no design-wise/movement register.

### 4d. Dhrn Outstanding + accrued interest — desktop `RP_DHRN_OS.cs` (4253) vs web `dhrn.outstanding`/`reports.dhrnOutstandingList`
- Desktop joins `DHRN_ISU_DATA` + **`DHRN_DATA`** (movement) summing `INT_AMT, INT_REC_AMT,
  DHRN_REC_AMT, UNCHAK_DHRN_REC`; reports per loan: party, mobile, PACKET_NO, DHRN_BILL, GOLD_WT,
  GOLD_DESC, INT_PRC, **accrued interest to report date** =
  `(DHRN_AMT−DHRN_REC_AMT)×INT_PRC/100×days÷MsIntYearDays` (RP_DHRN_OS.cs:2053), days = report-date −
  loan date. Aging by date.
- Web: outstanding = `principal − Σ DHRN_REC_AMT` only. **No accrued interest, no UNCHAK advance
  netting, no DHRN_DATA, no packet/collateral/mobile, no aging.**

### 4e. Reports present in web but thin, and desktop reports with NO web equivalent
Web has: sales/purchase register, trial balance, account ledger, GSTR-1/3B, stock valuation, old-gold,
bill-outstanding, sales-by-party/item, balance sheet (derived/approximate), monthly sales, day-book.
Desktop additionally has (no/weak web equivalent): **RP_CASH_BANK** (cash & bank book), **RP_INOUT**
(in-out/movement), **RP_REMINDER** (loan/payment reminders), **RP_DAY_WORK**, **RP_TRADING** (trading
a/c), **RP_BAL_ZOOM** (balance drill), **RP_DHRN_OS aging**, image/printed Crystal-report layouts.

## 5. Contra / Fine-JV (desktop `TR_CONTRA.cs`, 3849 lines)

- **Web `postContra`**: money only, single line (SR_NO=1), inline AC_DATA, no ROJ_MEL_DATA,
  **no FINE JV (metal journal) at all**, no multi-line, no remark.

## 6. Approval / Consignment — desktop `TR_APR_ISU.cs` (8294 lines) — NO web equivalent
Books: `APR ISU` (goods out on approval), `APR RTN`, `CON ISU`/`CON REC` (consignment), `CONSI PURC`,
`KARIGAR ORDER`. Tag-based item grid; writes `APR_DATA`/`APR_DETL`/`APR_IDTL` and `MAIN_STOCK`

core jewellery flow (goods given to customer/karigar to view/sell-or-return).

## 7. Jadtar / Fitting / Ghat job-work — desktop `TR_JDT_REC.cs` (8399 lines) — NO web equivalent

`GHAT REC` (**wastage/loss receipt**). Metal + stone (`WX`) movement with karigar, weight/touch/fine,
wastage. Writes job/detail tables + `MAIN_STOCK` + karigar fine. Web: `karigar.ts` exists but
`txn/jobwork-issue` & `jobwork-receive` pages are **179-byte stubs**; no jadtar/fitting/ghat/para flows.
