## Approval record — 2026-07-29

Every row has a disposition or a vector; no blanks remain.

**Validations** — of the catalogued business rules, the four not carrying desktop wording are
dispositioned: two WAIVED (a LAN-share image error handler and a rule gated on
`SSRegSrNo = 'HM285NEKU'`), one UI-LEVEL (fires between removing a tag row on screen and saving — the API
only ever sees a complete write set), and one newly IMPLEMENTED (`Please Insert Party Entry And Try.....`,
rejecting a voucher whose labour, pieces, gross-weight and net-amount totals are all zero).

**Computed fields** — all 23 catalogued cells carry a vector, `GV-PRLINE-001..005` plus
`GV-PRDETL-001/002`. The purchase family is deliberately NOT unified with the sale family:

| | Sale | Purchase |
|---|---|---|
| Line total | `Math.Round(sum, 0)` — whole rupees | `Format(sum, "0.00")` — paise kept |
| Item amount | fine × rate | **pieces × rate**, `Math.Round(…, 0)` |
| Weights | format-string, half-up 3 dp | same |

**Back-calculation direction is pinned** (`GV-PRLINE-002`): touch from fine ÷ net weight, rate from
conversion rate ÷ percentage, labour rate from amount ÷ pieces. Reading only the forward formula would
have inverted these operands.

**Defect fixed during this review:** `PR_DETL.TOT_AMT` was never written on the create path at all, and
the labour rate uses the configured `MsLbrRof` rounding rather than a fixed 2 dp.

**Recorded ambiguity, not guessed:** the tax-inclusive `NET_AMT` branch is gated on
`Val([43]) <> Val([58])`, where column 58 shadows the previous tax percentage — a UI change-detection
flag whose outcome depends on the operator's edit sequence and is not reproducible from a payload.
