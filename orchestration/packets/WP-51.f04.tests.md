## Goal

Finding F-04 of the WP-51 security review (2026-11-23, Medium, rated here as "breaks normal use"): the login limit (`/auth/login`,
10 per minute, `app.ts:534-536`) is keyed on `req.ip`, and Fastify is built without `trustProxy` (`app.ts:134-138`).
Every browser request arrives through the Next rewrite, so all users of all shops share one bucket: ten mistyped
passwords lock everybody out of login for a minute. This breaks normal use, so it is fixed before the feature work
ends. Write `web/apps/api/test/loginRateLimit.test.ts` with `buildApp` and `app.inject` (no database needed: copy
how `editionGate.test.ts` builds the app with a stub prisma; the login handler may answer 401/500 for the stub, the
test only looks for `429`):

1. Eleven failed logins for login name `a` from client `10.0.0.1` (header `x-forwarded-for: 10.0.0.1`, inject
   `remoteAddress: '127.0.0.1'` as the Next proxy) → the eleventh answers 429.
2. After that, a login for login name `b` from client `10.0.0.2` through the same proxy is **not** 429.
3. The same login name `a` from another client `10.0.0.3` is not 429 (the key is client IP plus login name).
4. A request that does not come from the trusted proxy cannot pick its own key by sending `x-forwarded-for`:
   with `remoteAddress: '203.0.113.9'`, eleven failed logins for login name `a`, each with a different forged `x-forwarded-for` → the
   eleventh is 429.

The implement packet will add an option `trustProxy` to `buildApp` (`BuildOpts`), default `'127.0.0.1'`, so pass
nothing for it. Record the red run in `orchestration/work/WP-51/red-f04.md`
(`pnpm --filter @datacare/api exec vitest run test/loginRateLimit.test.ts`).
