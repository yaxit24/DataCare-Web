## Goal

Write the study document for the menu **Report → HuId Report**. The desktop form is `RP_HUID` (2,731 lines). It
lists jewellery tags by their HUID (hallmark unique id) status. The web has a first version at `GET /reports/huid`
that covers the filters only. The next workers will write the case list and the tests from your document, so it
must state every selector, filter, column, total and key of the desktop form, each with a quoted citation.

## What to cover

1. The four views the catalog names (stock, inward, outward, all): how the operator chooses one, and the query
   each one builds. The catalog points at `RP_HUID.cs:1752-2189`; read beyond it wherever the code leads.
2. Every filter control (dates, party, product, group, item, book, HUID present or absent, search box) and the
   condition it adds to the query.
3. The grid: each column in order, its caption, its source column and its format; the sort order; the totals row.
4. The statements at `RP_HUID.cs:1754-1757` update `BAR_DETL`. A report that writes is unusual: state exactly what
   they change, when they run, and whether a hosted, multi-user web report should repeat that write. Put your
   conclusion under "Desktop weaknesses not to port" or under "Rules", with your reason.
5. Print: the rights check (the form shows the message "You Have No Print Rights....."), the template it prints
   and the parameters it passes. Search `extraction_output/rpt_xml/` for the template before saying it is missing.
6. Keyboard: Enter order through the filters, Esc, and any function keys.
7. Web today: what `web/apps/api/src/modules/reports/huid.ts` returns, which page shows it, which tests exist.
8. Gaps: each desktop behaviour the web lacks or does differently.

## Out of scope

- Writing code, tests or the case list.
- Other reports. The UAE variant.
