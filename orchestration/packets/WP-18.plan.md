## Goal

The study and the frozen case list for the menu Report → HuId Report are done (`orchestration/work/WP-18/`).
Turn them into (1) a design document a reviewer can check in ten minutes, and (2) the work packets that cheaper
sessions will run to build the report. You write no application code and no tests.

## Facts you need

- **The packet format** is described below, because `orchestration/PACKETS.md` is not in this worktree yet. Use
  `orchestration/packets/WP-18.cases.md` in this worktree as the model for the header and the brief.
  - A packet is a Markdown file. It starts with a title line and one fenced `json` block, then the brief.
  - Header fields: `id` (equal to the file name without `.md`), `wp`, `title`, `role` (one of `tests`,
    `implement`, `ui`, `verify`, `records`, `review`, `fix`), `tier` (`C` for a bulk model, `B` for a stronger
    one), `risk` (`B` for this package), `branch` (`agent/wp18-huid-report`), `dependsOn` (packet ids),
    `allow` (globs of the paths the session may create or change: as narrow as its output), `outputs` (files
    that must exist afterwards), `context` (files to read first, as `path` or `path:start-end`), `inline`
    (short `path:start-end` excerpts pasted into the prompt), `gates`, `limits` (`minutes`, `maxChangedFiles`,
    `maxDiffLines`).
  - Gates are objects: `{ "type": "cmd", "cwd": "web", "run": "pnpm typecheck", "timeoutMin": 15 }` or
    `{ "type": "cite", "file": "<path>", "requireSnippets": true }`.
  - The brief has `## Goal`, `## Facts you need`, `## Steps` or `## What to cover`, `## Out of scope` and
    `## Done when`. It is written for a model that has never seen the project: it names files and line ranges,
    the existing example to copy, the commands to run and the nearest wrong turn. "Done when" lines are checks.
  - Roles and what they may touch: `tests` writes tests only; `implement` writes API and domain code and cannot
    change tests; `ui` writes the page and its components and cannot change the API or tests; `verify` operates
    the browser and writes a verification record; `records` updates the catalog, backlog and generated views.
- **This machine cannot run database or browser tests** (no Docker). Local gates can only be
  `pnpm typecheck` (from `web/`), `node --check <file>` for `.mjs` files, and unit tests that need no database
  (`pnpm --filter @datacare/core exec vitest run test/<file>`). Database tests and the browser suite run on
  GitHub CI after a push. Say this in every packet whose work CI must prove, and make each such packet list the
  tests it wrote but could not run.
- **Size ceilings.** `web/apps/api/src/routes/txn.ts` and `web/apps/web/app/(app)/reports/[report]/page.tsx` are
  at their ceilings: a packet may add at most a one-line registration to `txn.ts` and nothing to the generic
  report page. A new file stays under 1,500 lines. The report gets its own route directory
  `web/apps/web/app/(app)/reports/huid/` and its own API route file under `web/apps/api/src/routes/`.
- **Decisions already made** are the eight numbered facts in `orchestration/packets/WP-18.cases.md`: three
  views (Stock, In, Out), the desktop stock rule, Print refused without the right, the Gold default, the first
  HUID column only, the date window and year, and no Counter or Item filter.
- **Read-only.** The desktop form updates `BAR_DETL` and uses a shared staging table; the study lists these as
  weaknesses not to port. The web report writes nothing.

## What to produce

1. `orchestration/work/WP-18/design.md`, at most 250 lines:
   - the resolver: its input (view, dates, filters, scope), the query for each of the three views as the
     desktop builds it (cite the study's lines, do not re-derive), the row shape, totals, and how the stock rule
     is expressed in PostgreSQL;
   - the API: route path and file, query parameters with validation, rights policy by menu caption, tenant,
     company, location and year scope, the response shape;
   - the page: its directory, the filter controls in desktop tab order, the three view buttons with their
     mnemonics, the grid columns per view, the search box, keys, and what is removed from the generic page;
   - print and export: template regions and columns, the rights check;
   - a table mapping every executable case in `cases.md` to the test layer and the packet that covers it;
   - the risks: what could silently give a wrong list or leak another tenant's rows, and the case that catches
     each.
2. The packets, in `orchestration/packets/`, each small enough for a bulk model (one role, one output, about
   400 changed lines at most):
   - `WP-18.tests-db.md`: database tests of the resolver through the real route, with the seed data from the
     case list's "Test data" section;
   - `WP-18.tests-ui.md`: the browser module `huidReport.mjs` and its registration;
   - `WP-18.api.md`: the resolver and its route (depends on tests-db);
   - `WP-18.screen.md`: the page in its own directory (depends on api and tests-ui); split print into its own
     packet `WP-18.print.md` if the design shows it is more than a small part;
   - `WP-18.review.md`: an independent review of the whole diff.
   Use tier `B` for the api packet and tier `C` for the others unless the design gives a reason.
3. State the order and what can run in parallel.

## Out of scope

- Application code, tests, the catalog and the backlog.
- Reopening the eight decisions.

## Done when

- `orchestration/work/WP-18/design.md` exists and every executable case of the case list appears in its mapping
  table.
- The packets listed above exist, each with a valid header and the five brief sections.
- Your report lists every decision you made that the owner might make differently.
