(`routes/approval.ts:162` schema `expectedVersion: { type: 'string', pattern: '^[0-9a-f]{64}$' }`, and the writer
compares inside its transaction). Files and sizes: `routes/fineJv.ts` 165 lines, `modules/finance/fineJv.ts` 695
lines (`postFineJv` :484, edit reads rows `FOR UPDATE` at :511, `editFineJv` :594), page
`app/(app)/txn/fine-jv/page.tsx` 410 lines. Put the version computation (the canonical write set of one Fine Jv
voucher passed to `modules/vouchers/version.ts`) in a new `modules/finance/fineJvVersion.ts` if it is more than about
30 lines. Compare the token **after** the `FOR UPDATE` read and before any write; a stale token throws the existing
version-conflict error class so the route answers 409 `voucher-version-conflict` (see how `routes/txn.ts:949` maps
it; do not edit txn.ts). The page keeps the `version` from its GET and sends it with PUT and DELETE; after a 409 it
shows the API message and keeps the operator's grid.

Rules: no test edits, no file past 1,500 lines, no change of desktop message texts, parameterised SQL only.
