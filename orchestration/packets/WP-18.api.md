## Goal

Build `GET /reports/huid` for the three desktop views (Stock, In, Out) exactly as `design.md` sections 1 and 2 describe, so that the tests of `WP-18.tests-db` pass. The report writes nothing.

## Facts you need

- Read `design.md` sections 1 and 2 first: they fix the SQL for each view, the stock rule, the row keys, totals, validation and scope. The three desktop SELECTs are inlined above (one line each); the study's table
  at `study.md:165-181` gives the condition per view. Do not re-derive; copy the conditions and the column list.
- The tests you must satisfy are in `web/apps/api/test/huidReport.db.test.ts`. Read them to learn the exact keys, status codes and error body. If a test contradicts the design, follow the test and report the difference.
- Pattern to copy: `routes/accountLedger.ts` (plugin with helpers `{prisma, auth, guard, readScope, sendReportPdf}`, query parsing, error mapping) and `modules/reports/accountLedgerReport.ts` (a resolver with a validation error class).
  The old `modules/reports/huid.ts` shows `withTxBudget` and the `::text` casts. Do not edit `huid.ts`.
- Registration: in `routes/txn.ts` replace the three lines `app.get('/reports/huid', auth, async (req) => REPORT_BUILDERS.huid(...))` (near line 4524) with one call `registerHuidReportRoutes(app, { prisma, auth, guard, readScope, sendReportPdf });`
  plus one import line. The file is at its size ceiling: the net change must be zero or negative lines. Nothing else in `txn.ts`.
- Policy: `routePolicy.ts:984` already has `route('Reports/HuId Report', ['GET /reports/huid'])`; leave it for this packet (packet `print` adds the export paths).
- Rules that are easy to get wrong: every value is a bound parameter; scope comes from `readScope(req)` and never from the query; add `tenant_id` conditions as the design says; the stock rule is a SUM of serial numbers in a grouped subquery (not a count);
  Stock ignores `from`; In and Out include both end dates; search runs after the query in the pure function `applyHuidSearch`. Supervisor decision: write that function in a new file `web/packages/core/src/huidSearch.ts`, export it from `web/packages/core/src/index.ts` the way the other kernels are exported, and import it in the resolver from `@datacare/core`; the page filters its loaded rows with the same function, so it must not depend on anything in the API. Its unit test `web/packages/core/test/huidSearch.test.ts` already exists and must pass (`pnpm --filter @datacare/core exec vitest run test/huidSearch.test.ts` runs here without a database); weights stay decimal strings and totals are summed with the decimal helper
  in `web/packages/core` (search for `Decimal` or the integer-thousandths helper; if none is usable, sum as integers of thousandths) and never as floats.
- Stock rows must carry `vchDate` (a hidden column) next to the visible `stkDate`, and every row carries hidden `prCode` and `grCode` (`B.PR_CODE`, `B.GR_CODE`); packet `print` needs them.
- Check each column name used in the SQL against the Prisma schema before using it; report any mismatch.

## Steps

1. Write `huidTagReport.ts`: types, `HuidReportValidationError`, `parseHuidQuery(raw)`, `applyHuidSearch(rows, text)`, `huidTagReport(prisma, scope, q)` returning `{view, from, to, columns, rows, totals}`.
2. Write `routes/huidReport.ts` with `registerHuidReportRoutes` and the JSON route only (exports come in packet `print`). 400 body `{error:'validation', message}`. Rights: `guard(req, reply, 'view')` as the other report plugins do, if they do; otherwise rely on the route policy.
3. Make the one-line registration in `txn.ts`.
4. Run `pnpm typecheck` and `pnpm lint` from `web/`. You cannot run the database tests here (no Docker); say so and name the tests CI will run.

## Out of scope

Exports (CSV, Excel, PDF), the page, any test, editing `huid.ts` or `REPORT_BUILDERS`, the data-type setting (no condition), the stock-merge setting (the company condition is always applied), a counter or item-code filter.
