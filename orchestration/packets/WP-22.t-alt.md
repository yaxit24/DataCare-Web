## Goal

Write the tests that define the alternate-year company (`CO_MAST.ALTER_YEAR = 'Y'`) before it is built. Pure date and key rules go in a core unit test
that runs without a database; the stored rows go in a database test.

## Facts you need

- Local gates: `pnpm typecheck`, `pnpm typecheck:tests`. Core unit tests can run here:
  `pnpm --filter @datacare/core exec vitest run test/fiscalYearAlt.test.ts`. They will fail until `impl-alt` adds the functions (expected); run it once and paste the
  failure (it must fail because the functions are missing, not because of a typo). Database tests cannot run here (no Docker); CI runs them.
- Functions the implementation will export from `@datacare/core` (`web/packages/core/src/fiscalYear.ts`, 67 lines now), to be tested by name:
  `alternateYearDefaults(today: {year:number, month:number}) => { coYear: string; yearMonth: string; opDate: string; clDate: string }` and
  `alternateYearKey(coYear: string, yearMonth: string) => string`. Since they do not exist yet, import them as
  `import * as core from '@datacare/core'` and call `(core as any).alternateYearDefaults`; add a comment that `impl-alt` removes the cast.
- Kernel vectors (desktop rule, study lines 164-169 and `cases.md:426-486`):
  - clock 16 Nov 2026 -> code `2026-2027`, month `11`, opening `2026-11-01`, closing `2027-11-01`, key `202611`.
  - clock 15 Feb 2027 -> code `2026-2027`, month `02`, opening `2027-02-01`, closing `2028-02-01`, key `202602`.
  - April boundary: clock 1 Apr 2026 -> code `2026-2027`, month `04`, opening `2026-04-01`, closing `2027-04-01`, key `202604`. March boundary: 31 Mar 2027 -> code `2026-2027`,
    month `03`, opening `2027-03-01`, closing `2028-03-01`, key `202603`.
  - `alternateYearKey('2026-2027','11')` is `202611`; month `7` is padded to `07`.
  Citations: `MS_YEAR.cs:1012 {{tMonth.Text = Strings.Mid(Conversions.ToString(DateAndTime.Today), 4, 2);}}`, `MS_YEAR.cs:1189 {{dataRow["CO_YEAR"] = Strings.Mid(tYearCode.Text, 1, 4) + tMonth.Text;}}`.
- Database: company `03` has `CO_MAST.ALTER_YEAR='Y'` (insert with the owner client; `CO_MAST` columns `CO_CODE`, `CO_NAME`, `LC_CODE`, `ALTER_YEAR`).
  Copy the setup from `masterSaveFidelity.db.test.ts:1-60` (229 lines). `createYear(runtime, {tenantId, coCode}, input)` returns `{coYear, opDate, clDate}`; after
  `impl-alt` it also returns `coYearKey`.

## What to cover

Core file: the five vectors above and the key function. Database file, one `it` per case id:
`year-create.alt.create-footprint-apr-dec` (`CO_YEAR '202611'`, `OP_DATE` 2026-11-01, `CL_DATE` 2027-11-01, `OLD_METHOD 'N'`, `YEAR_MONTH '11'`, `MAIN_USER 'op1'`),
`alt.create-footprint-jan-mar` (`'202602'`), `alt.second-year-same-month` (`'202711'`, first row unchanged), plus three more:
(1) the same alternate year twice is refused with `/already exists/` and one row remains; (2) a body field `alterYear: 'Y'` (or `oldMethod: 'N'`) on a standard company
(`02`, `ALTER_YEAR 'N'`) is ignored: key stays the typed code and `OLD_METHOD` `'Y'`; (3) a year created for `03` accepts a date check: `assertFiscalDateTx(tx, {...scope, coYear:'202611', coBook:'000'}, '2027-10-31')`
resolves and `'2027-11-01'` is outside (import as in `masterSaveFidelity.db.test.ts`), and `listYears` returns the stored key.
