- **Checkout:** `~/dc-wt/orchwt/specs-batch`, branch `agent/specs-batch-2026-11-23` @ `101fe4be`.
- **Type:** read-only audit. No application code was changed, nothing was run against a database, and Docker was not used.

## 0. Scope: what "reachable by a Lite tenant" means here

**How the scope was derived.** Every `app.<verb>('<path>')` registration in `api/**` (not test files) was joined to its rights form in `modules/rbac/routePolicy.ts`. Each form was then looked up in `FORM_EDITION` (`packages/core/src/editionTable.ts:258+`). A form counts as Lite when its tier is `L` or `platform` (`tierIncluded`, `packages/core/src/editions.ts:52`).

**Route counts.**

| Class | Routes |
|---|---|
| Lite form routes (`L` or `platform` form) | 328 |
| Higher-edition form routes, refused in Lite by the edition gate (`app.ts:461-469`, `editionGate.ts:34`) | 416 |
| Public, system or dynamic routes | 31 |

- **Public:** `/health`, `/ready`, `/auth/login|refresh|logout`, plus dev-only `GET /`.
- **System (any authenticated user, no form right):** `/me`, `/context/*`, `/lookup/:entity`, `/rate`, `/rate-groups`, `/party/:acCode/balance`, `/vouchers/recent|neighbour`, `/integrations/barcode|qr`, `/auth/password/change`.
- **Dynamic:** `@master` (`/masters/:name*`) and `@report` (`/reports/:report/*`). These resolve to a form per request and are edition-gated after resolution.

The full list with the form for each route was generated by a script and is not reproduced here. Re-run it with `python3 -I <scratch>/lite.py` from `web/`.

**Lite forms reached, by area:**
- Sales: Invoice, Return, Order, Order Cancel, Estimate, Wholesale, Tour/Approval, Approval Return, Hallmark.
- Purchase: Invoice, Return.
- Cash/Bank: Receipt, Payment, Contra, JV, Fine JV, Multi-Party Receipt, Daily Rate, Opening Bal.
- Inventory: Tag Opening, Print, Cancel, Stock Adjust, Item Opening.
- Masters: Accounts, Party, Items, Groups, Products, Taxes, Employees, Addresses, Companies, Years, States, Live Gold Rate Cfg, Auto Item.
- Reports: about 35 Lite reports plus the Crystal/Form layouts.
- Company: Balance TrFr.
- Utilities: Users & Rights, Backup, Data Refresh, Data Repair, Provision Company, Year-End Close, HDD Registry, Audit Log.

**A Lite fact that shapes every authorization finding.** In Lite the rights grid is hidden and every right is seeded `Y` for every user:
- `modules/rbac/userMaster.ts:117-145` `seedRights` inserts `FRM_VIEW/EDIT/DELETE/PRINT='Y'` for every `FORM_CATALOG` entry.
- D36 and `editionGate.ts:44-55` confirm this design.
- The rights-grid routes are refused in Lite (`routes/userMaster.ts:117-122`).

So inside a Lite tenant the only real privilege boundary is **admin (`LOGIN_CATG` starting with `A`) versus non-admin**. That boundary is enforced by the `ADMIN_ONLY` set (`routePolicy.ts:1188-1211`). Any Lite form route that is not in `ADMIN_ONLY` is available to every staff login.

## 2. Findings in detail

### F-01 High: the generic master list returns integration secrets to every Lite user

`api/modules/masters/master.service.ts:536-555`:
```ts
const rows = await withTxBudget(prisma, scope.tenantId, 'read', (tx: any) =>
  tx.$queryRawUnsafe(
    `SELECT * FROM ${q(config.table)}${where.sql} LIMIT ${n}`,
    ...where.params,
  ),
);
return jsonSafe(rows);
```

**How it is reached.**
- `GET /masters/companies` maps to `CO_MAST` (`configs.ts:197`).
- `GET /masters/gold-rate` maps to `DG_GOLD_MAST` (`configs.ts:289-290`, `MASTERS['gold-rate']` at `:470`).
- Both forms are Lite: `'Masters/Companies': 'L'` and `'Masters/Live Gold Rate Cfg': 'L'` in `editionTable.ts`.
- The routes need only `read`, and every Lite user has it (§0).

**The same columns are already classified as secrets.** The backup policy names them in `api/modules/ops/backupTenantConfigPolicy.ts:148-158`:
```ts
{ table: 'CO_MAST', column: 'URL_PWD', reason: 'D37 integration secret: web URL password' },
{ table: 'CO_MAST', column: 'MAIL_API', reason: 'D37 integration secret: SMTP mail key' },
{ table: 'DG_GOLD_MAST', column: 'API_KEY', reason: 'D37 integration secret: rate API key' },
```
The backup writes `NULL` for these (`ops/backup.ts:57-60`), but the live read API returns them in clear.

In Basic and above, `GET /masters/einvoice-gsp` (`E_MAST`) returns `ASP_PWD` and `E_LOGIN_PWD` the same way.

**Exploit.** Any counter-staff login opens DevTools, or calls `/api/masters/companies`, and reads the shop's SMTP API key and web-portal password. With them it can send mail as the business (for example, phishing the shop's customers) or sign in to the portal.

**Fix.**
- Make `listMaster` project an explicit column list: the form fields plus key columns, minus `BACKUP_EXCLUDED_SECRETS`.
- Return secrets as `"••••"` or a `hasValue` flag, and accept them only on a write-only update.
- Add a test that asserts no `looksSecret()` column carries a value in any `/masters/:name` response. `findSecretValuesInArchive` already shows the pattern.

### F-02 High: the rights table (`USER_SET`) is not company-scoped

**Rights check.** `api/modules/rbac/authorization.ts:144-152`:
```ts
`SELECT "FRM_VIEW","FRM_EDIT","FRM_DELETE","FRM_PRINT"
     FROM "USER_SET"
    WHERE "LC_CODE"=$1 AND "USER_NAME"=$2
      AND UPPER(TRIM(COALESCE("SUB_MENU",''))) IN (${placeholders})
    ORDER BY "row_id" LIMIT 1`
```

**Rights grid read** (`getUserFormRights`, `formRights.ts:27-35`) also has no `CO_CODE` filter.

**Rights grid save.** `api/modules/rbac/formRights.ts:92-96`:
```ts
await tx.$executeRawUnsafe(
  `DELETE FROM "USER_SET" WHERE "LC_CODE"=$1 AND "USER_NAME"=$2`,
  scope.lcCode, userName);
```
The rows are then re-inserted with the session `CO_CODE`.

The table does carry `CO_CODE`, and `seedRights` deletes per company (`userMaster.ts:123-128`), so the scoping is inconsistent. On the desktop each company was a separate SQL Server database, so `USER_SET` never needed `CO_CODE`. In the single web database it does.

**Exploit.**
- **Escalation:** user `ram` exists in companies 01 and 02 at location `01`. An admin restricts `ram` in company 02. The rights check picks the lowest `row_id` row, which is company 01's all-`Y` seed, so the restriction is ignored.
- **Silent wipe:** saving `ram`'s grid in company 02 deletes his company 01 rights too.

**Lite impact.** The grid routes are refused in Lite and every seed is `Y`, so Lite exposure today is limited. Rows imported from desktop data, or a tenant moving up an edition, inherit the bug immediately. It is rated High because it breaks the company boundary inside a tenant.

**Fix.**
- Add `AND "CO_CODE"=$n` (session company) to all three statements.
- Pass `coCode` into `authorizeFormTx`, `getUserFormRights` and `resolveAllowedForms`.
- Add a two-company test.

### F-03 Medium: company switch takes another company's identity without re-authenticating

**Which companies a user may select.** `businessScope.ts:53-65` lets a non-admin select any company that has a `LOGIN_MAST` row with the same `LOGIN_NAME`.

**What the switch does.** `sessionContextSelection.ts:443-450` then loads the target principal from that company's row:
```ts
const target = await loadPrincipalTx(tx, {
  tenantId: identity.tenantId, loginName: identity.loginName,
  coCode: scope.coCode, loginCoCode: current.row.loginCoCode });
// Explicit new web policy: another company's required credential reset cannot safely use this login identity.
if (target.passwordResetRequired) return fail('target-password-reset-required');
```

`loadPrincipalTx` (`authorization.ts:66-88`) prefers the selected company's row, so its `LOGIN_CATG` (role) and rights now apply. The password checked at login belonged to the login company's row. The target row has its own `LOGIN_PWD`, and it is never verified.

**Exploit.** `manager` is a staff user in company 01 with one password. A different person's `manager` login is ADMIN in company 02 with a different password. The company-01 user logs in to 01, selects 02, and acts as the company-02 admin.

**Fix (any one of):**
- Require the target row's password when switching to a company other than the login company.
- Bind a web identity to exactly one `LOGIN_MAST` row and grant company access explicitly.
- At minimum, never raise the role on a switch: use `min(role of login row, role of target row)`.

### F-04 Medium: one login rate-limit bucket for everybody behind the proxy

**Code.**
- `app.ts:135-139` constructs Fastify with no `trustProxy`.
- `app.ts:158` registers `rateLimit` with `{ global: false }` (in-memory store).
- `app.ts:534-536` sets `config: { rateLimit: { max: 10, timeWindow: '1 minute' } }` on `/auth/login`.

**Why the bucket is shared.** All browser traffic arrives through the Next rewrite (`apps/web/next.config.mjs:13-16`), so `req.ip` is always the Next server.

**Exploit.**
- An unauthenticated script sending about 10 bad logins a minute keeps the whole shop locked out of login.
- With several API replicas, each replica has its own bucket, which multiplies the brute-force allowance by the number of replicas. Per-account back-off (D34, `sessionContextLogin.ts:21-50`) still limits guessing per account.

**Fix.**
- Set `trustProxy` to the known proxy hop(s) and key the limit on client IP plus `loginName`.
- Use the Redis store, since Redis is already in the production compose file.
- Optionally also limit at the edge.

### F-05 Medium: Year-End Close and Balance Transfer are open to every Lite user, with years taken from the body

`routePolicy.ts` lists `POST /year-end/close` only in `UPDATE_POST_ROUTES`. It is not in `ADMIN_ONLY`. The Balance Transfer POSTs fall through to `create` (View suffices, `authorization.ts:155-161`).

`api/routes/txn.ts:7953-7963`:
```ts
app.post('/year-end/close', auth, async (req, reply) => {
  if (!guard(req, reply, 'create')) return;
  const b = body(req); const s = sess(req);
  return run(reply, 201, () => yearEndClose(prisma, {
      scope: scopeOf(req) as any, fromYear: b.fromYear ?? s.coYear, toYear: b.toYear }));
```

`modules/ops/yearEnd.ts:252-260` checks only that the two years are non-empty and different. `enforceRequestScope` (`businessScope.ts:300-308`) checks `coYear`/`CO_YEAR` but not `fromYear`/`toYear`. The same applies to `toYear` in the `routes/balanceTransfer.ts:53-80` handlers.

**Exploit.** Any staff login in a Lite shop can carry closing balances from an arbitrary year into an arbitrary (even non-existent) year. That rewrites opening balances for the company and is hard to undo.

**Fix.**
- Add Year-End Close and the Balance Transfer POSTs to `ADMIN_ONLY` (or `SCOPED_ADMIN_ONLY`).
- Classify them as `update` or `delete`.
- Force `fromYear` to equal the session year, and require `toYear` to exist in `YEAR_MAST` and be the next year.

### F-06 Medium: no CSP anywhere; print HTML is served on the app origin

**What exists today.**
- `app.ts:188-194` sets only `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and `X-XSS-Protection: 0`.
- `apps/web/next.config.mjs` has no `headers()` and there is no `middleware.ts`, so Next pages have no CSP, no `frame-ancestors`/XFO and no HSTS.

**Why print HTML matters.**
- API `text/html` print documents are opened top-level as `/api/...` on the app origin. Senders: `docChrome.ts` `docShell`, chequePrint, tagPrint, `/forms/layout` (txn.ts:6436-6440), `/stock/tag-print-screen/labels` (`tagPrintScreen.ts:125-128`).
- These documents contain inline handlers: `onclick="window.print()"` at `docChrome.ts:177`, `tagPrint.ts:496`, `chequePrint.ts:85`, and a `<script>` at `chequePrint.ts:96`.

**Exploit.**
- No exploitable injection was found; escaping is consistent (§3.4). But about 30 hand-written templates are one missed `esc()` away from stored XSS on the app origin. That script could make authenticated same-origin API calls (cookies are httpOnly but are still sent).
- Next pages can be framed by another site (clickjacking).

**Fix.**
- Add a strict CSP in Next `headers()`: `default-src 'self'; frame-ancestors 'none'`, plus HSTS.
- On API HTML documents, add `Content-Security-Policy: sandbox allow-modals; default-src 'none'; style-src 'unsafe-inline'; img-src data:`.
- Move `window.print()` into a hashed script.

Related functional note: `apps/web/app/(app)/txn/cheque-print/page.tsx:187-191` iframes an API page that sends `X-Frame-Options: DENY`, so the preview cannot render.

### F-07 Medium: the production compose file publishes the API directly

**Compose.** `deploy/docker-compose.prod.yml:68-69` has `ports: - '3000:3000'`. DEPLOY.md §8 says not to expose the API publicly.

**What `/ready` discloses.** It is public (`routePolicy.ts:17-29`) and returns the DB role name, `superuser`/`bypassRls`, RLS table counts and renderer status (`ops/health.ts:94-107`).

**Exploit.**
- The API is reachable on host:3000 without the edge proxy's TLS, headers or rate limit.
- `secureCookies` blocks cookie auth over plain HTTP, but `/ready` and the login endpoint are still exposed.

**Fix.**
- Bind to `127.0.0.1:3000:3000`, or use an internal network only.
- Reduce the public `/ready` response to `{ready}` and move the details behind admin `/ops/invariants`.

### F-08 Low: tenant header trusted by default
`app.ts:275-280`:
```ts
if (opts.allowTenantHeader !== false && headerTenant?.trim()) return headerTenant.trim();
```
`server.ts:94` passes `!config.isProduction`. A staging or demo deployment with `NODE_ENV` not set to production therefore lets any browser pick a tenant at `/auth/login` (credentials are still required). Only login uses `tenantOf`. Authenticated requests use the signed `tenantId` claim (`app.ts:351-371`), which is correct.

**Fix:** default to off (`=== true`), and strip `x-tenant-id` in the Next rewrite and at the edge.

### F-09 Low: database error text returned to clients
- `api/routes/txn.ts:1015-1026` returns `detail: (m?.[1] ?? msg).replace(/^ERROR:\s*/, '').slice(0, 200)` for any `Raw query failed` error.
- Masters return `DataError(dbErrorDetail(e))` (`master.service.ts:494-497`).
- Errors that escape `run()` reach Fastify's default handler (`app.ts:199-208`, `reply.send(error)`), which serialises `error.message` even on 500.

These messages contain Postgres text (column names, constraint names, values), not the SQL statement.

**Fix:** map known SQLSTATEs to stable codes, log the raw message with the correlation id, and return a generic 500 body.

### F-10 Low: legacy plaintext passwords and a timing signal
- `api/modules/auth/password.ts:31-35` uses `const ok = stored === candidate;` for non-Argon2 rows.
- `auth.service.ts:67-71` returns before any hash work when the user is unknown. `sessionContextLogin.ts:106-107` does the same when `rows.length !== 1`.
- A legacy row is rehashed only on the user's next successful login (`sessionContextLogin.ts:130`, `:166+`).
- Argon2id with library defaults is used for all new passwords (`password.ts:5-7`). That is good.

**Fix:**
- Use `timingSafeEqual` on the legacy comparison.
- Run a dummy `verify()` against a fixed Argon2 hash for unknown users.
- Run a one-off migration that Argon2-hashes every remaining plaintext `LOGIN_PWD` (hash the plaintext and keep `PASSWORD_RESET_REQUIRED='Y'`), so no plaintext stays at rest.

### F-11 Low: the legacy party-photo route does no validation
`api/modules/masters/party.ts:15-16`:
```ts
const b64 = String(dataUrl || '').replace(/^data:[^;]+;base64,/, '');
const buf = Buffer.from(b64, 'base64');
```
The route is at `routes/txn.ts:6303`. The newer `/masters/party-master/:code/photo` (`partyMaster.ts:1171`) does check PNG/JPEG magic bytes and a 2 MB cap.

**Exploit:** a user can store SVG/HTML or junk under any account code. It is harmless while the bytes are only shown in `<img>`, and becomes stored XSS if a future consumer renders them inline.

**Fix:** delete the route or route it through `decodeEntityImage` plus an existence check.

### F-12 High: generic master update allows company re-assignment through key normalisation (mass assignment)

`api/modules/masters/master.service.ts`, lines `:181`, `:264-279`, `:322-332` and `:457-494`:

```ts
const q = (id: string): string => '"' + id.replace(/[^A-Za-z0-9_]/g, '') + '"';   // strips, never rejects
...
const data = { ...source };                       // source = req.body
if (columns.has('CO_CODE')) data.CO_CODE = scope.coCode;
...
const keySet = new Set([...config.keyColumns, 'tenant_id']);         // exact-string compare on the RAW key
const setCols = Object.keys(data).filter((c) => !keySet.has(c));
const setSql = setCols.map((c, i) => `${q(c)}=$${keyParams.length + 1 + i}`).join(', ');
```

- **Route:** `PUT /masters/:name` (`app.ts:930-956`), which passes the raw `req.body`. There is no schema and no column allowlist. `normalizeBlankMasterValues` (`:383-396`) passes unknown keys through unchanged.
- **Why the guard fails:**
  - `bindMasterScope` forces `data.CO_CODE` (used in `WHERE`) to the session company.
  - A second body key `"CO_CODE "` (trailing space) or `"CO-CODE"` is not equal to `CO_CODE`, so it survives the key filter.
  - `q()` then normalises it to `"CO_CODE"` in the `SET` list.
  - Result: `UPDATE "AC_MAST" SET "CO_CODE"=$3 … WHERE "CO_CODE"=<session> AND "AC_CODE"=…`.
- **Same trick on other columns:**
  - `"AC_CODE "` or `"IT_CODE "` rewrites the business key, which is meant to be immutable, and skips the duplicate check.
  - `"LC_CODE "` re-stamps the location.
  - `"tenant_id "` is stopped by RLS `WITH CHECK`, so there is no cross-tenant write.
- **Create path:** on create the same key gives `INSERT … ("CO_CODE", …, "CO_CODE")`, which Postgres rejects, so create is safe from the company move. Create still writes any other table column (mass assignment, including `row_id` and `nonFormColumns`).
- **Verification:** found by reading the code (SQL sweep, confirmed by hand). It was not exercised at runtime.

**Exploit.** Any Lite user (every user has Edit) moves a party, item, group or tax row out of company 01 into company 02 of the same tenant, or renames its code. The change orphans vouchers and breaks the company boundary.

**Fix.**
- Allowlist body keys against `configuredColumns(config)` and the form fields, and reject anything else.
- Validate identifiers by rejecting rather than stripping: use `assertSafeIdent` from `security/sql.ts`, or `/^[A-Za-z_][A-Za-z0-9_]*$/`.
- Apply the key/tenant exclusion to the normalised name.
- Add tests with whitespace and hyphen variants of key columns.

### F-13 Low: `SMS_LINK` is a credential-bearing URL that is not on the secret list
`CO_SET.SMS_LINK` (`settingsInventory.ts:50`, `settingsCatalog.ts:230`) is returned by `GET /settings` and copied by `companyClone.ts:50`. `SECRET_COLUMN_PATTERN` (`backupTenantConfigPolicy.ts:32-33`) does not match it, so it is exported in the backup. Desktop SMS links usually embed `user=...&password=...` or an API key.

**Fix:** treat it as a secret: mask it on read, add it to `BACKUP_EXCLUDED_SECRETS`, and move the gateway credentials to env (`SMS_KEY` already exists in compose).

### F-14 Low: the `SECURITY DEFINER` sequence helper
`packages/db/prisma/migrations/20260829010000_company_restore_sequence_guard/migration.sql` has `EXECUTE format('LOCK TABLE %s IN SHARE ROW EXCLUSIVE MODE',p_table)` and returns the global `max(row_id)` across all tenants. It is granted to `app_user`.

**Exploit:** only server code can call it, and today only the (disabled) restore does. A future SQL injection could use it to stall writers on any table or to learn other tenants' row volume.

**Fix:** restrict the grant to a dedicated restore role, or return only `void`.

### F-15 Low (latent): `esc` without quote escaping
`api/modules/documents/docChrome.ts:7-11` escapes only `&<>`. No attribute interpolation exists today. Make it call `escapeHtml` from `reports/render.ts:12`, which escapes all five characters, and remove the roughly 10 duplicate local `esc` helpers.

### F-16 Info: lockout behaviour
Back-off starts after 5 failures, at 30 s doubling to a 15 min cap (`sessionContextLogin.ts:21-50`). Anyone who knows a login name can keep that account locked. `resetUserPassword` (`passwordAccount.ts:102-137`) does not clear `FAILED_LOGIN_COUNT` or `LOGIN_BLOCKED_UNTIL`. That is acceptable, but document it, and clear them on an admin reset.

## 3. What was checked and found clean

### 3.1 Tenant isolation (RLS)

**Policy bootstrap.** `packages/db/prisma/rls.sql` is generated from the catalog: every `public` table with a `tenant_id` column gets `ENABLE` + `FORCE ROW LEVEL SECURITY` and a `tenant_isolation` policy with `USING` and `WITH CHECK` (`tenant_id = current_setting('app.tenant_id', true)`) (`rls.sql:40-71`). It aborts if any tenant table is left without a policy (`:75-98`).

**Every model is tenant-scoped.** Every model in `schema.prisma` has `tenant_id` (an awk scan found none without it). The only tables outside RLS are catalog tables and `_prisma_migrations`.

**Runtime role.** `packages/db/setup_roles.sql` creates `app_user` with `NOSUPERUSER … NOBYPASSRLS` and a password of at least 16 characters; `audit_log` is insert and select only. Production compose connects as `app_user` (`docker-compose.prod.yml` `DATABASE_URL`). `/ready` fails if the role is superuser or BYPASSRLS, or if any tenant table is not forced (`ops/health.ts:72-107`).

**Tenant binding.** Every request query runs inside `withTxBudget` → `withTenant`, which sets `set_config('app.tenant_id',$1,true)` transaction-locally (`packages/db/src/tenant.ts:25-52`). The tenant comes from the signed JWT `tenantId` claim and is re-validated against `auth_session` on every request (`app.ts:351-353`).

**No owner or bypass connection.** The only `PrismaClient` is constructed at `server.ts:87`. The only direct `prisma.$queryRawUnsafe` calls outside a tenant transaction are catalog-only, admin-only reads: `ops/invariants.ts:31-50` and `ops/metrics.ts:118`. With no tenant set, RLS fails closed (NULL ≠ tenant_id). Many queries also add an explicit `tenant_id=$1` as defence in depth.

**One tenant per deployment.** Production pins `APP_TENANT_ID` and ignores `x-tenant-id` (`server.ts:93-94`; see F-08 for the non-production default).

### 3.2 Company, location and year isolation (IDOR)

**Request scope.** `enforceRequestScope` (`businessScope.ts:291-316`) refuses any top-level `coCode/lcCode/coYear` (either case, body or query) that differs from the session. It allows a `coBook` only if that book is active for the session company and location. Route adapters consume only `scopeOfRequest`.

**Voucher reads, updates and deletes** use the full desktop key from the session plus the validated book. Example: `getSale` filters `tenant_id, CO_CODE, LC_CODE, CO_YEAR, CO_BOOK, VCH_NO` (`sales/sales.ts:2336-2349`). Purchase, finance and stock vouchers follow the same pattern via `scopeOf`.

**Masters.** `bindMasterScope` overwrites `CO_CODE`/`LC_CODE` from the session and deletes `tenant_id` (`master.service.ts:264-278`). List and key queries add the scope (`:280-298`). `CO_MAST` generic writes are refused (`dedicatedWriter`, `configs.ts:200-201`).

**Context selection** checks company access (a login row exists, or the user is admin), plus location and year existence (`businessScope.ts:48-110`). See F-03 for the identity issue.

**Voucher navigation** requires read on a form that owns the book's `MAIN_BOOK` and uses an allow-listed table (`voucherNavigation.ts:31-66`, `vouchers/list.ts:16,71,193`).

**Residual (not a finding):** nested body fields are not checked by `enforceRequestScope`; handlers must keep ignoring client scope in nested objects. The sampled handlers do.

### 3.3 Authorization

**Every route has a policy.** The `onRoute` hook refuses to boot on any route without a policy or with an ambiguous one (`app.ts:167-186`). A registered route with no policy returns 500 (`:432-445`). A master or report name with no form mapping fails at boot (`app.ts:140-147`) or returns 403 at request time (`:483-487`).

**Central preHandler order:** auth → password-reset gate → edition gate → scope → `authorizeForm`, before any route handler (`app.ts:428-512`). Route `guard()` calls only re-check the marker.

**Action classification:** GET is `read`, POST is `create`, PUT is `update`, DELETE is `delete`. Explicit overrides exist for update-POSTs, print routes, read-POSTs and delete-POSTs (`routePolicy.ts:1137-1186`, `1246-1265`). Print, export and PDF routes, including `/reports/:report/export.*`, require `print` (`:1283-1300`).

**Admin-only routes** (`routePolicy.ts:1188-1211`): users and rights, backup and restore, audit and metrics, provision company, renumber, data refresh, data repair. Data repair also keeps scope validation (`SCOPED_ADMIN_ONLY`).

**Logical restore is disabled** by containment (`txn.ts:4627`, `packages/core/containment.mjs:89-93`, 503).

**User admin.** User listing does not select `LOGIN_PWD` (`rbac/users.ts:152-160`). Admin password reset applies the password policy, hashes with Argon2 and revokes the user's sessions (`passwordAccount.ts:102-137`). The new password is never echoed.

### 3.4 Input validation, files and output encoding

**SQL injection.** Values are bound as `$n` throughout. The interpolation sweep is in §2.1 / Appendix A. Identifiers go through `q()`/`qid()`/`quoteIdentifier` or allowlists. Numeric `LIMIT`/`OFFSET` are clamped: `stock.ts:684-685`, `stoneDmCf.ts:757-758`, `listMaster` ≤ 500, `lookup` ≤ 50, `recentVouchers` ≤ 200, `dataRepair` ≤ 200.

**Date filters** accept only `YYYY-MM-DD` (`txn.ts:838-850`). Reports are scoped to the session year.

**PDF.** Size is capped (`ReportTooLargeForPdfError` → 422, `txn.ts:4464-4471`). The Playwright renderer has JS disabled, is offline, aborts every request, has `file://` unreachable and limits concurrency (`reports/render.ts:325-366`). Residual: Chromium uses `--no-sandbox` unless `PDF_RENDERER_SANDBOX=1`.

**Path traversal.** The layout and spec loaders strip names to `[\w.-]` before `resolve(SPEC_DIR, …)` (`forms/formLayoutEngine.ts:25-33`, `reports/reportEngine.ts:72-75`). No other route reads the filesystem. The tag-print "default file" is validated against `PRINT_MAST` rows (`stock/tagPrintScreen.ts:170-195`).

**Uploads.** Uploads are base64 JSON only; no multipart parser is registered. Images have PNG/JPEG magic-byte detection, a 4 MB cap and a 6 MB route `bodyLimit`, and are served with the stored MIME plus `nosniff`. SVG cannot be uploaded. The exception is F-11.

**Downloads.** `Content-Disposition` filenames are built only from sanitised or allow-listed parts (`backupFilename.ts`, `xlsx.ts:70`, `voucherPrint.ts:64`, `isReportSlug`).

**CSV formula injection** is neutralised (`reports/reportCsv.ts` `csvCell`).

**Print HTML escaping.** Every traced string interpolation in about 30 document templates is escaped. Templates are not stored in the database; Crystal and WinForms layouts are repo JSON. `/estimate/pdf` takes typed input only, with a 64 KB cap.

**Web DOM sinks.** No `dangerouslySetInnerHTML`, `innerHTML`, `document.write` or `srcdoc` in `apps/web`. `openDocument` only opens `/api/...` hrefs. There are no open redirects.

### 3.5 Authentication and session

**JWT.** HS256 is pinned, with issuer and audience checks and a `typ` check separating access from refresh tokens (`auth/jwt.ts:70-119`). Production requires `JWT_SECRET` of at least 32 characters that is not a known weak value (`ops/runtimeConfig.ts:66-75`).

**Access tokens** last 15 minutes and are re-validated against `auth_session` (revocation, epoch) and a fresh `LOGIN_MAST` principal on every request (`app.ts:351-371`, `authorization.ts:61-89`). Deleted users and role changes therefore take effect immediately.

**Refresh tokens** last 7 days. A random 256-bit `jti` is stored hashed and compared with `timingSafeEqual`. Each refresh rotates the token, and reuse revokes the session (`sessionContextRefresh.ts:77, 190-210, 230-261`). Logout revokes the session (`app.ts:613-627`).

**Cookies** are `httpOnly`, `SameSite=Strict` and `path=/`, with `Secure` in production (`app.ts:149-156`, `runtimeConfig.ts:94`). The API has no Bearer or query-token path.

**CSRF.** There is no token. Protection comes from `SameSite=Strict`, JSON-only bodies and no CORS plugin; optional context-epoch headers are checked when present (`app.ts:353-360`). This is adequate. Residual: it does not protect against a sibling subdomain on the same site.

**Login.**
- One generic error message for every failure.
- Per-account exponential back-off (`sessionContextLogin.ts:21-50, 115`).
- Duplicate credential rows are refused (`:106`).
- Legacy plaintext passwords are upgraded to Argon2id with a forced reset (`:130, :166+`).
- The password policy follows NIST 800-63B (8-128 characters, common-password list, refuses passwords built from the login name or company code) (`password.ts:51-91`).
- `Cache-Control: no-store` is set on auth, context and `/me` responses.

### 3.6 Item 6: JWT in a URL query string

**Not present.**
- No `?token=`, `access_token`, `jwt=` or `query.token` appears anywhere in `apps/web` or `apps/api/src`.
- `requireAuth` reads only `req.cookies.access` (`app.ts:345`).
- Report, print, export, xlsx and PDF links carry only filters and voucher keys.
- `Referrer-Policy: no-referrer` is set on API responses.
- Request logs record the route template, not the URL (`app.ts:213, 259-272`; `disableRequestLogging: true`), so even a stray query string would not be logged.

### 3.7 Secrets and data exposure

**Data Backup.** `GET /backup` is admin-only. It writes `NULL` for `BACKUP_EXCLUDED_SECRETS`, including `LOGIN_MAST.LOGIN_PWD` (`backupTenantConfigPolicy.ts:148-158`; `ops/backup.ts:57-60`). Tenant-shared tables are exported only from an explicit allowlist. `auth_session`, `api_command_receipt` and the audit tables are excluded (`:133-142`). There is a test-enforced `SECRET_COLUMN_PATTERN` scan (`:32-33, 177-193`). Gaps: F-13 (`SMS_LINK`), and the live API path F-01.

**Data Export** is not a Lite form.

**Logs.** No secrets were found in log calls. The login failure log carries only a reason code (`app.ts:578-583`). Audit rows hold user, company, method, route template and status.

**Production configuration** refuses `SEED_DEMO` and fake messaging (`runtimeConfig.ts:76-80`). The dev seed uses `DEMO_PASSWORD` from env, hashed.

## 2.1 SQL injection sweep (`$queryRawUnsafe` / `$executeRawUnsafe`)

There are 927 `${…}` interpolations inside raw-SQL template literals outside tests. **No exploitable SQL injection was found.** The one real issue is identifier normalisation in the generic masters (F-12, High). There are two Low items (A-1, A-2). The full triage is in Appendix A.

## Appendix A: SQL interpolation triage

There were 927 interpolations in the inventory. A subagent swept them, plus about 40 calls whose SQL is held in a variable or goes through a wrapper, which the inventory missed (tagStock, orderTagReports, graphReport:397, accounting:171, reportBind, rpAll/salesQuery, dataRefresh, seedCompany, partyMaster:822/1047, balanceTransfer, estimateReset, master.service).

**Result: no exploitable SQL injection.** Every interpolated value is one of the following:
- a constant fragment;
- a ternary over literals keyed on a validated mode;
- a `$n` index;
- an identifier from an allowlist, a static map, or the `information_schema`/`pg_attribute` catalog;
- a numeric value passed through `Number()`.

There is no `Prisma.raw`/`Prisma.sql` and no `+` concatenation into Unsafe calls. No ORDER BY or sort column comes from the request.

**Findings from the sweep:**
- **F-12 (above).** Identifier normalisation in the generic masters. This is not classic SQLi, but it is the one real issue the sweep found.
- **A-1 Low.** `limit` is interpolated after `Number()` with no lower bound or integer check. `limit=-1` yields `LIMIT -1`, which Postgres rejects, giving a 500 error, not an injection.
  - Locations: `vouchers/list.ts:74,127` (`GET /vouchers/recent`), `ops/audit.ts:42,46`, `masters/master.service.ts:543,551`, `masters/lookup.ts:89,122,189,240,397`, `stock/stock.ts:398,406`.
  - Fix: `Math.max(1, Math.trunc(...))`, as `stock.ts:684` already does, or bind `LIMIT $n`.
- **A-2 Low/info.** `reports/reports.ts:169-172`: `AND b."MAIN_BOOK"='${mainBook.replace(/[^A-Z0-9_ ]/g, '')}'` is sanitised by hand inside a literal. The only callers pass the constants `'SALES'` and `'PURCHASE'` (`:204`, `:213`). Bind it as `$n` anyway.
- **Not findings.** The `.replace(/'/g,'')` calls in the master `typed()` helpers, tagSplitRows, tagCancelRows and stockAdjustLots strip apostrophes from values (desktop parity), and the values are then bound. They are not used as SQL escaping.

**Clean by category:**
- **Reports:**
  - `${dt}` comes from `dateWhere()` placeholders, and `${yr}` is a fixed `' AND "CO_YEAR"=$2'`.
  - `${filterSql}`/`${fl}` come from `filterWhere()` over static `REPORT_FILTER_BINDINGS` (`reportFilters.ts:115-160`).
  - reportBind uses static contracts, a hash-pinned spec and allowlisted tables. rpAll uses `p()` placeholders over static `SALES_SPECS`.
- **DB-stored identifiers:**
  - `BOOK_DATA.BOOK_TBL_NAME` is only compared to constants. `numbering.ts` regex-validates it and checks it against the catalog.
  - `BOOK_TBL_DETL` is checked against a regex and `information_schema` (`dataRepairOps.ts:541-570`).
  - `COL_MAST` input is allowlisted (`columnSettings.ts:48-78`). Settings use `qcol()` over `SETTING_CATALOG` keys only.
- **Sales:** saleReturnNumericUpdate takes the identifier regex and `format_type` from `pg_attribute` (`:691-717`). salesOrder null-column updates are limited to `ORDER_WRITE_TABLES` and the prior-row columns.
- **Stock and masters:** static `SOURCES` maps, constant column lists, and `distinct(column)` called only with literals. In lookup.ts an entity like `__proto__` only throws (500), and is not injectable.
- **Restore** (disabled): identifiers are `""`-escaped, and the uploaded manifest must equal the live `loadBackupSchemaManifest()` before any DDL-derived SQL runs (`ops/backup.ts:412-418`).
- **Auth:** `credentialSql` and `selectSessionSql` are module constants with bound parameters.
