## Crucial semantic corrections and invariants

- `D/TR_SALE.cs:14979`-area logic calls `DC_Main.LedrCash` then rejects accumulated receipt cash above `MsCashLimit`. Several older prose specs describe this as “over cash limit ⇒ require PAN.” That is not this sampled save branch. PAN, cash limits, tax rates and statutory policies need separate source-derived rules and separately approved current regulatory configuration. Never encode a prose summary as the oracle without the branch.
- Tag identity is not merely a visible tag string. The sale save resolves `TAG_NO` with `VCH_SRNO` from `MAIN_STOCK` + `BAR_DETL`; old/new tag reuse and location must be preserved. `D/TR_SALE.cs:14998` onward and `D/TR_TAG_SPLIT.cs:6245` onward are references.
- Stock is a movement ledger with `ITM_SIGN`, pcs/gross/net/fine/other attributes, not a single quantity decrement or `TAG_STOCK.available` field. `D/Ac_Stock.cs:98` (`Sale_Stk`) changes selected stock weights according to `MsStockRptView` at 112–113 and adds differences under `MsSlAndTagWtDiff` at 125. Sales and physical tag weight can differ legitimately.
- Money and fine metal are separate accounting dimensions. `Ac_Ledr` writes amount DR/CR and signed gold/silver fine legs; amount balance alone is insufficient. Account routing depends on `BOOK_DATA`, `BOOK_DETL`, item groups, tax master, company/mode and sometimes historical registration branches. Convert hardcoded customer/license branches into explicit configuration or formally retire them; do not silently universalize them.
- Desktop calculations use `Strings.Format`, `Conversion.Val`, `Math.Round` and branch-specific precision. .NET `Math.Round` default ties-to-even is not interchangeable with a blanket half-up decimal rule. Freeze stage-by-stage rounding, rate unit, zero/blank handling, manual overrides and negative/refund behavior, then use exact decimal arithmetic with reference fixtures.
- In the sampled sale, header/details/repost use a SQL transaction begun at 15166; `Ac_Ledr.Sales_Ledr`, `Ac_Rojmel.Sales_Rojmel`, `Ac_Tax.Sales_GST`, `Ac_Stock.Sale_Stk`, and `Dm_Sale_Detl` run at 16118–16130; commit is 16136. `Vch_Remark` and further tax adjustment work appear **after commit** at 16137 onward. Do not claim the whole legacy save is atomic; web should consciously close partial-write gaps while preserving successful outcomes.
- A sale also marks order details sold and approval issues received, and clears tag approval state at 16110–16115. Edit/delete must restore/link-recompute those states, not just reverse financial rows.
- `BtmSchm` and `Module_Schm` are transfer/reset utilities, not the ordinary savings installment module. `NextEmp.exe` is a messaging companion per catalog, not evidence of a missing payroll suite. `AllImage.rar` contains an ASP.NET WebForms app as well as image stores; it is additional workflow/style evidence.

## Step-by-step evidence recipe for every workflow

1. Freeze source binary/version, source file hash, database backup hash, company/location/year/book/settings and role. Record unresolved decompilation/reachability issues.
2. Extract actual UI control contract from runtime or source: tabs, grids/popups, fields, defaults, readonly/hidden conditions, required validations, keyboard focus and shortcuts; link every field to its persisted/read-back destination or derived formula.
3. Define exact precondition rows and deterministic actions, including tag/packet/lot identity and all referenced documents; snapshot affected tables and report inputs.
4. Execute the **desktop** scenario on a controlled Windows copy where feasible; capture screen state, calculation values at each stage, successful/blocked actions, before/after SQL deltas and emitted document. If runtime blocked, label evidence as source-derived and list the exact remaining sign-off step.
5. Implement corresponding web rule with server-authoritative context/authorization, decimal precision, full transaction boundary, concurrency/idempotency and compensating/outbox handling for external side effects.
6. Run the same actions in web UI; compare displayed fields and focus behavior, persisted reload, normalized row-by-row table differences, independently recomputed ledger/stock/tax/balance invariants, reports and print/export.
7. Edit an input changing quantity/rate/tender/link; ensure old effects reverse once and fresh effects post once. Attempt edit/delete with downstream dependencies; apply the specified block or reversal workflow. Delete/cancel where allowed and compare restored baseline plus retained audit history.
8. Exercise two sessions, double-click/retry, timeout after commit, process failure between stages, stale record update, insufficient permission, wrong company/location/year, lock date, missing/deleted master, duplicate serial and negative/overallocated stock/credit. Verify error is actionable and no partial state persists.
9. Validate representative printed/PDF/label artifacts visually against desktop reference and numeric data; test scrolling, dense keyboard entry, large grids, Unicode, browser zoom and intended device widths. Do not require mobile UI to reproduce a desktop grid pixel for pixel, but preserve access to its workflow depth.
10. Attach evidence IDs, immutable web commit, tool versions, executed tests/results and reviewer. Status progresses `inventoried → mapped → specified → implemented → statically checked → desktop-replayed → web-replayed → reconciled → user-accepted`. Missing desktop/runtime evidence stays explicit; never use “complete” merely because route and save test exist.

## End-to-end acceptance journeys

- New company/location/year → roles/books/masters/rates/openings → supplier purchase → tag/stone/image/label → scan retail sale with old gold + order advance + scheme + cash/card/UPI → receipt/settlement → part return → ledger/stock/GST/Rojmel/profit + invoice and credit note.
- Customer design order/advance → metal/stone issue → all configured manufacturing stages and partial receipts → tag creation → partial and final delivery → order tracking and artisan/WIP balances → cancel/reverse one intermediate action under dependency policy.
- Customer repair receipt and images → karigar issue → partial repair return → customer delivery/labour bill → custody and repair reports.
- Approval/consignment/tour issue → partial return → sale remaining → settle tour/party → confirm stock ownership, custody, profitability and history.
- Gold and silver wholesale/bullion booking → partial rate fixing → delivery/fine settlement/interest → hedge reversal → fine and money ledgers and booking outstanding.
- Scheme opening → several multi-member/multi-rail collection vouchers → gold conversion → partial sales redemption → final payout/maturity → passbook and expired-member state, then authorized reversal.
- Dhiran with several packets → interest-only collection → partial principal and one packet release → renewal across year → final settlement/rate-cut → letters/khata/loan reports and reverse of last receipt.
- Physical stock count with missing/unexpected tag → approved adjustment → split/retag/weight change/counter/location transfer → scanner/label/image and stock reports.
- Full day/month/year close: cash/bank reconciliation, tax export/e-invoice sandbox, trial balance/P&L/balance sheet, year carry-forward including open documents, verified backup restore, restart/retry and migration reconciliation.

Each journey must be run with real-shaped anonymized fixtures for at least the selected production modes, gold/silver/diamond variants, two companies/locations, prior-year references, multiple users and the agreed high-volume envelope. Source-specific custom branches must receive an explicit include/replace/retire decision; a generic generic-CRUD proof is insufficient.
